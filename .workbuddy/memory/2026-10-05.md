**Kitco 的确切配置**（实测三要素齐全，与 PM 说的 11 条不同，严格匹配 6 条）：
```json
{ "itemSelector": "div.flex.flex-col", "linkSelector": "a[href^='/news/article/']",
  "titleSelector": "a[href^='/news/article/'] span", "publishedAtSelector": "time" }
```
标题在 `a` 内的 `span`；链接是 `/news/article/YYYY-MM-DD/slug` 相对路径；`time` 带 `dateTime="...-0400"`。**配了 publishedAtUtcOffset 反而会覆盖正确时区**。

**新的静默失效模式（比 403 更隐蔽）**：
- 403 → 抓取报错，能发现

- **选择器取自浏览器 DOM** → 报 `no items matched (html)`，PM 在浏览器里验证通过但服务端抓不到

**主题页验证的正确方法**：条目链接是 `/items/{20+位小写字母数字}`，**不是 `/item/`**。我第一次用 `/item/[a-f0-9]{8}` 全部返回 0，误以为页面空。修正后 gold/silver 各 1 条。

## 2026-10-06 切换到全 Docker 环境

**用户的疑问**：只在 Docker 里看到 pg，前 后端环境在哪。**答案：之前是混合形态**（数据库在 Docker 容器、api/worker/web 是 Windows 上的 Node 进程），而且昨晚那些进程已随会话结束停掉。**现已切到项目自带的全 Docker 方案**。

**切换步骤与踩的坑**：

- **FRED**（定期统计数据，Date 是数据归属期）→ 必须推算发布日，且周末不更新会导致 3 天间隔 → 必然 `stale`。这是**数据性质决定的**，不是 bug

**判断依据**：先看源的 `Date` 到底是什么语义，再决定要不要推算发布延迟。不要一律套用FRED 的做法。

## 2026-10-06 Phase 4：并发噪声归因（我第 5 次同一个错误，被纠正）
后端报告「全量 25 → 31、同文件三次 0/18、15/3、0/18」，我判断是**测试库名撞名**（每文件派生 `aihot_test_fNN_test`），**就改了 `package.json`（并发 6→1、超时 120s→180s）**。

## 2026-10-06 三个发现（都值得单列）
**① 「零失败」可能是「文件根本没跑」**（前端发现，我核实属实）
`tests/mcp.test.ts` / `tests/outlet-invariants.test.ts` 报 `Cannot find package '@modelcontextprotocol/client'` → **文件级崩溃不计入 fail 统计**，所以数字看起来比实际干净。
**根因是框架的 `Dockerfile:24` 的 `npm prune --omit=dev`**：它把只在测试里用的 devDependency 从镜像剪掉了。该包在根 `package.json:27` 有声明，宿主 `node_modules` 里有，**只有镜像里没有**。
⚠️ **两种修法都不通**（我试了）：整份挂 `node_modules` → 覆盖镜像里 `@aihot/*` 的 workspace 相对符号链接，`@aihot/contracts` 解析失败；只挂该包 → `docker run` 报 `invalid mode`。**需要 `npm i -D` 装进镜像，或在有 git 与完整依赖的环境跑这两个文件。**
**教训：统计「通过率」时必须分清「断言全过」和「文件加载失败」，后者在多数统计工具里都不算 fail。**

**② 并发噪声的真正根因（后端两次反复后给出证据，我核实成立）**
`tests/databases.ts:64` 的库名是 `${name}_f${pid}_${suffix}`，**含 `process.pid`** → 同文件重跑 pid 变、库名变，`globalSetup:48` 的 `dropCopies` 按固定 `copyPattern` 匹配**清不掉** → 残留累积到 `CREATE DATABASE` 撞名（`42P04 duplicate_database`）。
⚠️ **「跑前清残留库」是正解，并发/串行只是残留速度的差别。** 我上轮改 `package.json` 为串行是治标，已回退。
**我清库后重测基线：692 tests / 652 pass / 40 fail** —— 之前那个「15」是残留库导致文件崩溃、fail 被低估。

**③ 前端与后端的一次危险操作（未造成损失）**
前端在修契约时跑了 `git checkout -- packages/contracts/src/site.ts`，**只回滚了未提交的改动、后端已提交的 45 行新增保住了**（我核实 `git diff --stat` 显示 45 insertions 仍在，5 个关键导出都在）。**如果那45 行是未提交状态，就会被抹掉。**
**流程改进：动共享文件前先 `git diff` 确认它相对 HEAD 的状态；`git checkout --` 是破坏性的，且默认丢弃未提交改动。**
