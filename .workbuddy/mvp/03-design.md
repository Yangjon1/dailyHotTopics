# 03 · 设计方向：贵金属 + 大宗商品 + 股债热点站

> 日期：2026-10-05 | 设计师：颜好看 | 阶段：Phase 2 设计方向
> 三轴刻度：**DESIGN_VARIANCE = 4**（数据栅格要规整，可预测） / **MOTION_INTENSITY = 3**（金融用户要静态与可信，动效只用于状态确认） / **VISUAL_DENSITY = 7**（资讯站密度 4-5 → 行情站密度 7，低于 8，叙事内容仍可用卡片，行情块一律无框）

## 一、对标品牌分析

### 1.1 逐个拆解

**Bloomberg Terminal**
- 视觉语言：近黑底（`#000` 系）+ 琥珀/橙前景 + 全等宽字型 + 极窄字号（10-12px）+ 零留白 + 分区用 1px 线而非色块。信息在屏幕上「铺满」，靠**位置**建立层级，不靠留白。
- 密度处理：靠「分区 + 固定行高 + 键盘优先」把密度拉满；没有卡片，只有 24 列网格。数字用等宽字体保证纵向对齐。
- 数字呈现：全等宽、右对齐、正负号显式、颜色编码（涨绿跌红，欧美约定）。
- 软肋：**这是为盯盘 8 小时设计的人机界面，不是阅读界面**。琥珀色在黑底上长时间阅读疲劳严重；字号低于 12px 中文完全不可读；零留白导致「不知道该看哪里」——新人完全无法上手。

**Kitco**
- 视觉语言：以金/铜色为品牌骨架，白底，价格表用极细分隔线（`#e8e8e8` 级），表格密度中等。
- 数字呈现：`Current Price` 独立一行大字（`4,175.30 USD/oz`），下方挂 3日/7日/30日/60日/6月/1年/5年/10年/15年 的多周期涨跌表——**这张表是 Kitco 最值得抄的东西**。
- 软肋：金色在白底上作为文字几乎不可读（`#FFD700` on 白 ≈ 1.4:1），金色大面积用变成「珠宝电商」而非「行情终端」；多周期表列太多、首屏溢出一屏半；首页导航层数过深。

**东方财富 / 金十数据**
- 视觉语言：高信息密度门户，多列分区，每区一个横条标题 + 列表；品牌色为红/金。
- 数字呈现：**涨红跌绿（中国约定）**，数字带单位后缀（`4,175.30`），百分比定点两位。
- 软肋（这是我们要避开的）：**涨跌色被当装饰色用**——品牌红 = 涨红，读者无法区分「这是数据的红」还是「这是品牌的红」；首页 8-9 个横条模块堆叠，层级靠边框而非顺序，扫读时所有区域权重相同；字号混乱（同一个页面上 11/12/13/14/16/18px 六种共存）；广告位与内容位同权重。

**Trading Economics**
- 视觉语言：极朴素白底，几乎无装饰，表格纪律极强（列头左对齐文本、右对齐数字、单位写进列名、细横线无竖线、无斑马纹）。
- 数字呈现：全世界一致的等宽数字 + 右对齐 + 括号表示负数。
- 软肋：视觉层级过平——所有数字权重相同，**重点不突出**；没有涨跌色（对期货/大宗是硬伤）；品牌感为零。

**Investing.com**
- 视觉语言：绿/红双色主导，广告与弹窗密集。
- 软肋：颜色噪音——涨跌色、涨跌背景块、按钮色、图标色全是红绿体系，**全屏没有一处中性锚点**，导致「一眼扫过去不知道该看哪个数」。这是我们最需要避开的东西。

### 1.2 结论：对标品牌

**对标 A：Bloomberg Terminal —— 取「数字纪律」，不取「黑底荧光」**
- 取：等宽数字 + 右对齐 + 显式正负号 + 分区用 1px 线不用色块 + 键盘可达的列表结构。
- 不取：黑底（用户要浅色）、荧光琥珀前景（浅底上不可读）、10px 字号、零留白。
- 为什么是它：它定义了「专业用户如何读数字」。这个站的读者是投资/决策视角，数字纪律是唯一不可妥协的部分。

**对标 B：东方财富 + 金十数据 —— 取「行情入口与涨跌约定」，不取「模块堆叠」**
- 取：**涨红跌绿**这条中国约定；品种分类的横向导航；财经日历式的「时点 + 事件」组织方式。
- 不取：首页多横条堆叠、品牌色与涨跌色同色、字号层级混乱、广告位与内容位等权重。

**辅助参照：Kitco 的多周期涨跌表**（同一品种的 3日/7日/30日/N月/N年 涨跌表）—— 这是本站「事件详情页关联行情」的直接模板。

### 1.3 共同软肋总结（我们的差异化机会）

1. **涨跌色 = 装饰色的通病**（东方财富/金十/Investing）。→ 我们的解法：**品牌主色与涨跌色正交**。品牌用青（teal），涨跌用红/绿，两套颜色永不混用。这是本站最关键的一条视觉决策。
2. **没有中性锚点**（Investing）。→ 我们的解法：中性色占 88%，红绿各只在数字上出现，每屏 `accent` 可见处 ≤ 2。
3. **表格纪律普遍松散**。→ 我们的解法：第 8 节的数字规范逐条锁死（tabular-nums、右对齐、显式正负号、无斑马纹、单位进列名）。

## 二、配色方案

### 2.1 为什么不用金色做主色（先讲清楚，因为这是最容易被要求的）

金色是低亮度低对比色：`#FFD700` 在白底上对比度约 **1.4:1**，远低于 WCAG AA 的 4.5:1。想让金色成为「品牌文字色」，唯一出路是把它压到深金/古铜（`#8A6E2A` 一类），而那已经是「棕色」，不再有金属感。更致命的是**语义冲突**：本站的数据对象就是黄金。如果界面骨架是金色的，读者无法区分「金色 = 品牌」还是「金色 = 黄金这个品种」。

**决策**：
- 金色**只**出现在两个地方：(a) 图表/数据系列里的「黄金」曲线（多系列图中）；(b) 贵金属分类标签的 1px 左规则线（不用填充块）。**永不作为按钮底色、链接色、卡片边框色、页面背景。**
- 品牌主色沿用 AIHOT 已有的**青（teal）**——延续用户在 AI 站的视觉记忆，同时天然与红/绿正交。

#### 降级与隔离（重要）

现有 `--hot: #b3402a` 与 `--ok: #2f7d5c` **保留但语义收窄**：

- `--hot` / `--hot-soft` → **仅**表示「热度/爆」（热榜第一名、爆点标签）
- `--ok` / `--ok-soft` → **仅**表示「操作成功」（复制成功、提交成功）
- **禁止**把 `--hot` 当涨色、`--ok` 当跌色使用。二者色相与 `--up`/`--down` 邻近，混用会让「最热的那条」和「涨得最多的那条」视觉同义。

#### 配比校验（对齐 token-standard §6）

| 层级 | 占比 | 本站落点 |
|---|---|---|
| 中性 | 88% | `--bg` / `--surface` / `--ink-*` / `--line` |
| 强调 | 5% | `--accent`（品牌）+ `--up`/`--down`（数据） |
| 语义 | 3% | `--warn` / `--alert` |
| 效果 | <1% | `--accent-soft` 选中底 |

**每屏 `--accent` 可见处 ≤ 2**（顶部导航选中项 + 主 CTA 或筛选选中态，二选一）。`--up`/`--down` **不计入 accent 配额**（它们是数据色，不是品牌色），但**同屏红绿单元格总数上限 40**——超过就说明该用表格而不是卡片流了。

### 2.4 黄金题材的落地方式（不俗套的具体做法）

1. **不做金色 Logo 大标**。BrandMark 用青。
2. **不做金色渐变标题**（P0 红线：且渐变文字一律禁止）。标题纯色 `--ink`。
3. **黄金只在三处出现**：(a) 图表中黄金那条曲线用 `--metal-gold`；(b) 「贵金属」分类标签左侧 1px 规则线；(c) 品种元数据行的 `AU9999` 代码前缀用等宽字重 590 + 微弱下划线。
4. **提供「金属感」的手法不是颜色，是质感**：1px 发丝线、等宽数字、tabular 对齐、极轻阴影（`0 1px 2px rgba(24,32,36,0.025)`，沿用现值）。这比金色更有机构感。

## 三、字体方案

### 3.1 三个声音词（选型前必须先定）

**冷静、仪器、克制** —— 对应实物：一台实验室里的金属元素分析仪面板 + 1970 年代证券交易所的打印终端。

按此去找：窄体（condensed）无衬线做表头与标题（面板刻度感）、等宽数字做数据（仪器读数）、长中文正文用系统字（可读性优先）。

### 3.2 字体栈（**改动：现状是纯 `system-ui`，Windows 上落到 Segoe UI + 雅黑，数字用 Segoe UI 的比例数字，行情表列对不齐**）

```css
/* A1 — 字体 */
--font-display: "Roboto Condensed", "Archivo", "PingFang SC", "Microsoft YaHei", "Noto Sans SC", sans-serif;
--font-body:    "Roboto",          "Archivo", "PingFang SC", "Microsoft YaHei", "Noto Sans SC", sans-serif;
--font-mono:    "Roboto Mono", ui-monospace, "Cascadia Mono", Consolas, "SFMono-Regular", monospace;
--font-num:     "Roboto", "PingFang SC", "Microsoft YaHei", sans-serif;  /* 数字专用：tabular-nums */
```

**为什么是 Roboto 三兄弟而不是 Inter：**

- **Roboto** 由 Christian Robertson 设计，其骨架直接参照 DIN（德国工业标准字体），而 DIN 是全球金融终端的事实标准字体。**选择 Roboto 等于选择「仪器面板」的声音**，这是本站最核心的一条排版决策。Inter 没有这条血统，且是当前 AI 生成站点的默认字体，必须避开。
- **Roboto Condensed** 用于标题/表头/分类标签：窄体让 3 日 / 7 日 / 30 日这类周期表头在窄列里塞得下，也让长品种名（`布伦特原油` / `LME 三个月期铜`）不折行。窄体 = 密度感。
- **Roboto Mono** 只用于代码 / API 路径 / Key / 时间戳（精确到秒）/ 品种代码（`AU9999`、`XAU`），**不用于价格**（价格用 `--font-num` + tabular-nums，避免等宽字体的呆板感）。
- 三兄弟同骨架、同一作者，无混排割裂感；Google Fonts 全覆盖，woff2 子集化后约 30-40KB（中文字体不打包）。

**中文字体策略（重要决策）：**
- 中文**不打包 webfont**（思源黑体全字集 5-10MB，会毁掉首屏）。走系统栈：`PingFang SC`（macOS/iOS）→ `Microsoft YaHei`（Windows）→ `Noto Sans SC`（Linux/兜底）。
- **混排处理是有意的**：`Roboto Condensed` 只作用于拉丁字母与数字（Yahoo Finance / Bloomberg 的表格都这样处理），中文落到 PingFang / 雅黑。拉丁窄体 + 中文常规体在表格里混排是被验证过稳定的方案，读者不会察觉断裂。
- Windows 雅黑的字重只有 regular/bold 两档，所以 `font-weight: 510/590` 在 Windows 上会被合成或回退。**正文中文只用 400/700 两档**；中间字重的诉求（510/590）只对拉丁与数字生效。这是一个 Windows 特有的坑，必须在实现时验证。

### 3.3 字号阶梯（沿用现有 12/14/16/18/20/24/32/40 骨架，新增 11 与 13 两级用于数据区）

| Token | px | 行高 | 字距 | 用途 |
|---|---|---|---|---|
| `--text-2xs` | **11** | 1.4 | 0.02em | 表头、单位、脚注（**下限，不可再小**） |
| `--text-xs` | 12 | 1.5 | 0.01em | 元数据、时间戳、标签 |
| `--text-data` | **13** | 1.4 | 0 | **表格单元格 / 价格 / 涨跌幅**（新增，密度核心） |
| `--text-sm` | 13.5 | 1.65 | 0 | 列表摘要（FeedItem 摘要行） |
| `--text-base` | 14 | 1.6 | 0 | 正文（现状 14/1.5 → 1.6，中文更透气） |
| `--text-md` | 16 | 1.5 | 0 | 小标题 |
| `--text-lg` | 18 | 1.4 | -0.005em | 卡片标题 |
| `--text-xl` | 20 | 1.35 | -0.01em | 节标题 |
| `--text-2xl` | 24 | 1.3 | -0.012em | 页标题（现状） |
| `--text-3xl` | 32 | 1.2 | -0.018em | 数字大屏 / 报告刊头 |
| `--text-4xl` | 40 | 1.15 | -0.02em | 极少量，强调用 |

**硬约束**：正文与数据文字**不得低于 12px**。Bloomberg 的 10px 是为拉丁数字设计的，中文与百分比符号（`%` 是窄字符）在 10px 下不可读。

### 3.4 字重（三级体系在中文下的落地）

| 级别 | 字重 | 用途 | 中文可用性 |
|---|---|---|---|
| Read | 400 | 正文、表格数字、摘要 | 雅黑/PingFang 正常 |
| Emphasize | **510** | 表头、小标题、按钮文字 | 仅拉丁/数字；中文回退 500 |
| Announce | **590** | 页标题、品种名、大号数字 | 仅拉丁/数字；中文回退 700 |

### 3.5 字距规则

- 正文（13-18px 中文）：`0`
- 小字（11-12px）：`0.01em – 0.02em`（小字需要加字距才不糊）
- ALL CAPS / 周期表头（`3D` `30D` `YTD` `AU9999`）：`0.08em`（等宽/窄体本身字距紧，必须放开）
- 数字：`0`（`tabular-nums` 已保证等宽，加字距会破坏对齐）
- 标题（≥24px）：`-0.01em – -0.02em`

### 3.6 数字字体规范（本站硬需求）

```css
/* 所有价格、涨跌幅、成交量、日期数字、期数 */
.num {
  font-family: var(--font-num);
  font-variant-numeric: tabular-nums;
  font-feature-settings: "tnum" 1, "lnum" 1;

/* 代码、API 路径、Key、精确到秒的时间戳、品种代码 */
```

## 四、间距 / 密度规范

### 4.1 密度定位：从 4-5（AI 内容站）提到 **7（轻驾驶舱）**

| 维度 | 现状（AIHOT 内容站） | 本目标 | 差 |
|---|---|---|---|
| 基准字号 | 14px | 13px（数据区）/ 14px（正文） | -1 |
| 卡片内边距 | `p-5 sm:p-6`（20/24px） | `p-4`（16px） | -20% |
| 列表行垂直间距 | 16px | **12px** | -25% |
| 栅格 gap | 16px | 12px | -25% |
| 行情表行高 | （无此组件） | **32px**（紧凑）/ 36px（舒适） | — |
| 单屏可见信息条数 | 约 4-5 条卡片 | **行情行 ≥12 条 + 事件摘要 3 条** | **约 2.5-3 倍** |
| 节间距（桌面） | 64px | 48px | -25% |

**为什么不是 9-10（Bloomberg 级）**：本站在 Windows 浏览器本地运行，读者是「读事件 + 看关联行情的投资视角」，不是「盯盘的手速视角」。密度 7 是「一屏能扫完一段完整表格，也能读完 3 条事件摘要」的平衡点。再往上，长中文摘要会开始难读。

### 4.2 间距系统

**保留 4px 基准网格**（与 Tailwind 默认一致，91 个 tsx 已在此网格上写）。禁止 5/7/13/22/30 等非标值。

| Token | 值 | 新增用法 |
|---|---|---|
| `--space-0.5` | **2px** | 表格单元格上下内边距（紧凑）、徽章 |
| `--space-1` | 4px | 图标与数字、增减号与数值 |
| `--space-1.5` | **6px** | 行情行内元素间距 |
| `--space-2` | 8px | 同组元素、chip 之间 |
| `--space-3` | 12px | **列表行垂直内边距 / 栅格 gap** |
| `--space-4` | 16px | 卡片内边距 |
| `--space-5` | 20px | 模块间距（现状 24 → 20） |
| `--space-6` | 24px | 区块间距 |
| `--space-8` | 32px | 大区块 |
| `--space-12` | 48px | 页面级节距（现状 64 → 48） |

### 4.3 行高 Token（把密度变成 Token 而非临场值）

```css
--row-h-data:   32px;   /* 行情表数据行 */
--row-h-data-lg: 36px;   /* 舒适模式 / 可点击行 */
--row-h-head:   28px;   /* 表头 */
--row-h-list:   44px;   /* 移动端可点击列表行（≥44px 触摸目标，WCAG 2.5.5） */
```

### 4.4 栅格与容器

**保留**：`--gutter-l/r`（`max(16px, env(safe-area-inset-*)`）、`.bleed` 通栏工具类、236px 侧栏、48px 手机顶栏（`--bar-h`）。

**改动 1 — 拆分容器宽度**：

```css
/* 保留现状，用于文章/日报（长文阅读） */
--page-max-reading: max(1100px, calc(200dvh - 236px));   /* 不动 */

/* 新增：用于行情表 / 热榜 / 全部动态（需要更多列） */
--page-max-data:    max(1440px, calc(300dvh - 236px));
```

理由：现状 `--page-max-wide: max(1200px, calc(270dvh - 236px))` 在 21:9 屏上会拉到约 1900px，但站里**根本没有表格组件去填这个宽度**，结果是留白空旷 + 文字行长失控。行情页用更宽的容器 + 多列表格，宽才有用。

**改动 2 — 列数**：桌面 12 列 / 平板 8 列 / 手机 4 列，gap 12px（现状 24px）。
**改动 3 — 断点**：保留现状自定义断点（`sm 641 / md 768 / lg 961 / xl 1280 / 2xl 1536`）。**注意 `lg` 是 961px 而非 1024px**，这是 AIHOT 为平板横屏特意调过的，保留不动。

### 4.5 圆角

**保留现状六级**（`mark 5 / control 8 / tile 10 / card 12 / panel 14 / sheet 16`）。这套克制、且被 91 个 tsx 引用，不动。

**新增规则**：
- 行情表 / 表格**不加圆角**（表格是网格，圆角会破坏对齐感）
- 涨跌标签用 `--radius-mark`(5px) 或全圆角 pill，二选一，**不混用**
- 卡片圆角**上限 12px**（`--radius-card`），禁止 ≥24px 的过度圆滑

### 4.6 阴影

**保留现状**（极轻）：`--shadow-card: 0 1px 2px rgba(24,32,36,0.025)`、`--shadow-card-hover: 0 3px 12px rgba(24,32,36,0.055)`。

**禁止**：任何元素的 `border` + `box-shadow blur ≥ 16px` 同时出现（幽灵卡片）；毛玻璃装饰。

### 5.3 图标使用规范（Spec 条目）

```css
/* 图标尺寸 Token —— 16 / 20 / 24 三级，不允许其他值 */
--icon-inline: 16px;   /* 行内：chip、表格单元、按钮内 */
--icon-button: 20px;   /* 按钮内、导航项 */
--icon-standalone: 24px; /* 独立：空态、页头、分类入口 */
```

| 规范项 | 规则 |
|---|---|
| **stroke-width** | 24px 用 `1.75`（Lucide 默认 2 在浅底上偏重）；**16px 用 `1.5`**（必须降，否则 16px 下笔画粘连糊成一团）；20px 用 `1.7`。**这是唯一的例外规则，全项目不得再出现第四个值** |
| **颜色继承** | 一律 `stroke="currentColor"`，**不传 `color` prop**。颜色由父级 `text-*` 决定。这保证图标在任何表面、任何主题、任何涨跌语义下都自动协调 |
| **尺寸单位** | 传 `size={16}` 数字 prop（Lucide React API），或用 CSS 变量 class。禁止写成 `width`/`height` 字符串 |
| **fill 变体** | 只有 3 个图标允许 `fill="currentColor"`：GitHub 标、BrandMark、`Bookmark`（已收藏态）、`BellRing`（预警开启态）。其余全部 `fill="none"` |
| **无障碍 — 装饰性** | 紧邻可见文本的图标：`aria-hidden="true"` + `focusable="false"`（Lucide 默认已设，显式不写） |
| **无障碍 — 独立按钮** | 纯图标按钮**必须**有 `aria-label`，且**必须** 44×44px 触摸目标（图标 20px + `p-3`）。**禁止**只靠 `title` 属性 |
| **键盘** | 图标按钮参与正常 Tab 序，`:focus-visible` 用现有 `outline: 2px solid var(--accent)` |
| **禁止** | 禁止用图标代替文字标签表达功能（图标 + 文字共存时图标纯装饰）；禁止同一语义在不同页面用不同图标；禁止混用其他库或手写 SVG（**Logo / 品牌标 / 行情专用图形除外**） |

## 六、页面改造清单

> 每页格式：现状问题 → 改成什么样 → 为什么

### 6.1 首页 `/`（每日精选）

**现状**：`<h1>精选</h1>` + 分类 Tab + `HotTopics` + `Timeline` 卡片流。纯资讯结构，第一屏没有任何价格。手机上是顶栏 + 分类 + 热榜 + 卡片流。

**问题**
1. **投资/决策视角的用户第一眼看不到任何数字**——这是本站最核心的错位。用户打开一个贵金属站，第一诉求是「现在金价多少、今天涨跌多少」，现在这个答案在页面之外。
2. `.hide lg:block` 把分类 Tab 和搜索整块藏在桌面端——桌面用户失去分类切换能力，只能靠 URL 参数。
3. 首屏是三张同尺寸卡片（HotTopics），黄金题材没有任何视觉锚点。

**改成什么样**
- **第一屏加一条「行情带」（Quote Bar）**：一条通栏、无框、1px 上下线的横向带，横向滚动（手机）/ 8-10 个品种（桌面）。每格结构固定为四层：`品种代码`（`AU9999`，mono，11px，`--ink-3`）→ `最新价`（`--text-data` 13px，`tabular-nums`，`--num` 色）→ `涨跌幅`（`--text-data` 13px，`tabular-nums`，`--up`/`--down`）→ 一条 60px 宽的 24h 迷你走势线（`--sparkline`，现有 `features/hot/Sparkline` 直接复用）。涨跌幅**必须**带显式 `+`/`-` 符号与 `▲`/`▼`（色弱可读）。零值显示 `—`。
- 行情带**不放在卡片里**，用 `border-t border-b border-line` + `--surface` 底；上方一行是分类 Tab（贵金属 / 大宗 / 股债 / 全部），当前选中项用 `--accent` 下边线 2px 标识。
- 恢复桌面端的分类 Tab 与搜索（去掉 `hidden lg:block`），搜索框收进顶栏（详见 6.8）。
- HotTopics 保留，但**降级为「今日三条」**：`NO.01` 标记 + 标题 + 一行关键数字（如「金价 +1.24%，创 9 个月新高」）+ 24h 热度走势，去掉大图。
- Timeline 卡片：`p-5 sm:p-6` → `p-4`，摘要 14px/1.75 → 13.5px/1.65，右侧固定一条 88px 宽的「关联品种 + 涨跌幅」列（无图时不显示该列）。

**为什么**：行情带是本站对用户诉求的第一回答，且它一次性建立了 tabular-nums、右对齐、涨跌色这三套规范——用户从这里开始就进入「这是数据界面」的心智。行情带无框通栏（VISUAL_DENSITY 7 的硬要求：数据块禁通用卡片容器），避免首页变成「卡片里套数据条」的双重边框噪音。

### 6.2 全部动态 `/all`

**现状**：`FeedItem` 卡片流 + 分类/频道筛选 + 标签 chip + 天数分组（`DayHeader`，`bleed` 通栏灰条）。

**问题**
1. 纯时间序资讯流，对「这个品种最近发生了什么」零支持——金融读者的第一个检索维度是**品种**，不是时间。
2. `--page-max-wide` 在宽屏拉到 1900px，但单栏卡片列表吃不掉这个宽度，右侧整块空着。

**改成什么样**
- **新增首列「品种筛选条」**（横向 sticky，`z-10`，`--surface-2` 底，1px 下线）：全部 / 黄金 / 白银 / 铂金钯金 / 铜 / 原油 / 股指债。每个 chip 右侧带该品种当日的涨跌色小方块（`--up`/`--down`），让用户在筛选时就看到行情方向。
- **列表从单栏变双栏（≥1280px）**：左 2/3 资讯流（时间序），右 1/3 sticky「该品种 7 日事件 + 关联品种行情」侧栏（1px 左边线分隔，不用卡片）。宽屏宽度被真正用起来。
- `FeedItem` 增加一个**紧凑行模式**（默认开启，可切换卡片模式）：单行 = 时间 + 品种标签 + 标题（14px，1 行截断）+ 关联涨跌幅。单行行高 44px（触摸目标达标），一屏 12+ 条。
- `DayHeader` 保留（这是现状的好设计：`bleed` 通栏 + 可折叠，是时间轴的分节），但日标题右侧补当日「贵金属综合指数」或「BTC-情绪代理指标」式的**一个汇总数字**——给时间分节点一个金融含义。

**为什么**：品种优先于时间是金融资讯的基本组织逻辑。加右栏让 1900px 的容器宽度产生价值而不是空旷。紧凑行模式直接解决信息密度诉求（密度 4-5 → 7）。

### 6.3 热点榜 `/hot`

**现状**：`Lead`（NO.01 大卡，含封面图或 HeatPanel 走势）+ 后续名次条目 + 火花线 + `Delta` + `Faces` 参与者头像。**352 行，全站最重的页面。**

**问题**
1. **NO.01 一张卡就吃掉近半屏**，剩下的名次是 40px 高的条目——信息密度极不均衡。专业用户要的是「能一次扫完 10 名」的榜单。
2. `Lead` 的 `HeatPanel`（`aspect-[2/1]` / `16/10` 走势面板）与封面图二选一，占了 `xl:grid-cols-[1fr_0.72fr]` 的一半宽度——走势图的价值在于横向对比，单独放大一张毫无意义。
3. `BADGES` 用「爆 / 新 / 发酵中」单字 + tooltip。中文单字 badge 信息量太低，且 tooltip 鼠标依赖 = 触屏不可达。
4. `Faces`（参与者头像）与站的内容定位（资讯而非社区）不匹配。

**改成什么样**
- **改成「可排序榜单表」**（本项目最需要的新组件）：
  - 列：排名 / 标题（占满剩余宽）/ 关联品种 / 热度指数（13px tabular 右对齐）/ 24h 走势（60px sparkline）/ 6h 变化（`Delta`，tabular 右对齐）/ 首报时间（11px `--ink-4`，右对齐）
  - 排名列宽 40px（`01` `02` … 用 `--font-num` + `font-weight:590` + `tracking-[0.08em]`，沿用现有 `pad(rank)` 的 `00` 补零思路），前三名用 `--rank-1/2/3`，第四名起用 `--rank-rest`
  - 行高 32px（`<table>` 或 `div` grid），无斑马纹，只有 `--line-soft` 横线
  - 每行右侧一个 16px `ChevronRight`（hover 时出现），点击进入事件详情
  - 表格头 sticky（`top: var(--bar-h)`），`--bg` 底 + `--line-strong` 下沿
- **表头提供排序控件**：默认按「6h 变化」降序（这是热度榜的核心信息），另有「热度指数」「首报时间」两个次级排序，排序状态用 `ArrowDownUp` 图标 + `--accent` 标出。
- **NO.01 特殊化但不占屏**：在表格上方保留一条 88px 高的「今日最热」横条（不是 400px 大卡）——`NO.01` + 标题（18px，一行截断）+ 一句关键数字 + 热度指数 + sparkline（120px 宽，横向）。它在视觉上突出（`--surface` + 1px `--line` + `--shadow-card`），但在高度上不失控。
- **徽章改双字**：爆 → `突发`、新 → `首报`、发酵中 → `发酵中`。11px，`--radius-mark`，`--up-soft`/`--accent-soft`/`--warn-soft` 底。`title` 属性保留作为补充说明，但**语义必须写在可见文字里**（触屏可达、无障碍可读）。
- **`Faces` 移除**，替换为「`7 家媒体`」这样的文字（现状 `Voices` 已有「等 N 个来源」，只是格式统一）。理由：本项目无社区，「参与者」是无意义的概念。

**为什么**：榜单的本质是「可扫读的排序结果」，不是「Top 1 的展示 + Top 2-10 的附属」。表格式能把屏幕从「1 + 9」变成「10 × 全部可见」，密度从 3 直接到 7。去掉 Faces 是去掉一个不属于这个产品的社交化装饰。

### 6.4 事件详情页 `/story/:id` 与单条 `/items/:id`

**现状**：`ArticleLayout` 三栏（左栏 来源/目录，右栏 评分理由/主题/标签），`prose` 长文，13.5px/1.8 的评分理由，AI 徽章、评分标签、Sources 列表、ReadingProgress、`item.original` 外链 + StarButton + 更多菜单。

**问题**
1. **右栏有「评分」但没有「行情」**。这是最大的错位：一个贵金属事件页，用户最想知道「这件事对金价影响多大、现在金价多少」。
2. 左栏的 `facts`（来源 / 作者 / 时间）占了整个左栏顶部约 120px，但这三项在投资者眼里是元数据，优先级低于「这件事影响了哪个品种」。
3. `prose` 正文 17-18px/1.8 是优秀的中文长文排版（**这是资产，保留**），但金融事件正文里几乎必然包含**数据表**（央行利率表、多周期涨跌表、持仓表），`.prose table` 的样式（`border-collapse: collapse` + 1px 全边框 + `display:block` 横向滚动）是新闻表格不是金融表格——无 tabular 对齐、无涨跌色、无右对齐。

**改成什么样**
- **左栏顺序倒置，改为「事实面板」**：
  1. **受影响品种**（置顶）：`AU9999` / `XAU` 标签 + 当前价 + 涨跌幅 + 一条 24h sparkline。这一块用 `--surface-2` 底 + 1px 边框，`--radius-card` 12px。**这是整个页面唯一允许 `--accent` 出现的非交互元素。**
  2. **多周期涨跌表**（Kitco 参照）：`3日 / 7日 / 30日 / 90日 / 1年` 五个数字，每个 `+1.24%` 形式、13px tabular 右对齐、涨跌色。桌面横向一行，手机 2×3 网格。
  3. 来源 / 作者 / 时间（现状 `facts` 降级到这里，`--text-xs`，可用 `<details>` 折叠）
  4. 本项目目录（`outline`，保留）
- **右栏加「事件时间线」**：该事件的多个来源报道按时序排列（时刻 + 来源名 + 一行标题），替换现在的「AI 评分理由」位置——**评分理由保留但折叠进 `<details>`**（`AI 评分` 不是投资决策依据，不该占首屏）。这个改动同时解决 P0-3 的「AI 味」。
- **`.prose` 表格升级为金融表格**（见第 8 节）：`.prose table` 移除 1px 全边框（改 `--line-soft` 横线），数字单元 `tabular-nums` + 右对齐，加 `.prose table .num` 支持，涨跌数字自动挂 `--up`/`--down`。
- 阅读进度条（`ReadingProgress`）保留——这是现状的好设计。

**为什么**：事件页是「从信息到决策」的转折点。左栏置顶行情 = 用户读完摘要后立刻能校验自己的判断。多周期表是 Kitco 验证过的信息结构。把「AI 评分」折叠 = 去掉 AI 味 + 把产品重心从「AI 认为」移到「市场发生了什么」。

### 6.5 日报 / 周报 / 月报 `/daily` `/weekly` `/monthly`

**现状**：`ReportLayout` + `Nameplate`（刊名字形，`h-[50px]→h-[98px]`）+ `SectionPage` + `Rows` + 纸张色（`body:has(.report-shell)` 把 bg 调成 `color-mix(bg 60%, surface)` 的微调纸色）+ 往期存档按月分组（`daily-archive.tsx` 的 `archiveGroups` + 大日期数字 `text-[24px] font-black tracking-[-0.03em]`）。

**问题**
1. **「合订本」概念过重**。`Nameplate` 刊头 + 纸张底色 + 月份分节 = 一份「杂志」。但日报的核心消费场景是**每天扫一眼当天的关键数字**，不是「翻阅合订本」。
2. 存档页 `Rows` 每行是「日期 + 标题 + N 条」，日期 24px `font-black` —— 一个 24px 的黑体数字只为了显示「05」，在密度 7 的目标是浪费。**这个 `font-black` 还很接近 AI 生成模板的味道**（大号超粗数字 + 大字距负值的组合）。
3. 日报正文是 `.prose`（17-18px/1.8），在「扫读日报」场景下过慢。
4. **完全没有行情**。日报的黄金内容是「今日金价 +1.24%，白银领涨」这类结论，但现在只有文字。

**改成什么样**
- **当日日报（`/daily`）拆成两层**：
  - **顶部「今日盘面」条**（新增，无框通栏）：`[核心 3 个品种的价/涨跌幅] | [关键事件 3 条，每条一行「时刻 + 一句话结论 + 关联品种涨跌色方块」]`。这是日报的「报眼」，替代现在的大 Nameplate。
  - **下方日报正文**：字号 17px → **15px**，行高 1.8 → **1.7**，段落间距 `1.2em` → `1em`，容器 1100px → **900px**（行宽缩短，提升扫读速度）。段落仍每行 40+ 中文字。
  - Nameplate 刊头**降级**到 44px 高的单行（`h-[50px]` → 固定 44px），只作为「日报 · 2026-10-05 · 第 218 期」的一行元信息，**保留纸感但不再当主角**。报刊感是气质，不是信息。
- **存档页密度重做**：
  - 日期数字 24px `font-black` → **13px tabular `--ink-3`**（`font-weight: 400`）
  - 每行补一个「该期关键数字」列：`+0.86%`（`--up`/`--down`，tabular 右对齐，56px 宽）
  - 每月分组头加「当月日均条数 / 当月最大单日涨跌」两个小数字
  - 行高 32px，`divide-y` 无卡片容器
  - 保留 `beijingDate` / `weekdayShort` 的时区正确性逻辑（这是现状的正确实现，不动）
- **周报 / 月报**：增加「周期涨跌汇总表」（参照 Kitco 多周期表），周报按品种列出本周涨跌，月报列月度涨跌 + 关键事件时间线。两者共用同一 `QuoteTable` 组件。

**为什么**：日报的第一消费动作是「扫」，不是「读」。把 17px/1.8 的杂志排版改成 15px/1.7 + 顶部盘面条，能让一屏承载的信息量翻倍，同时保留纸感与刊头作为品牌气质。存档页的 24px 黑体数字是典型的 AI 模板特征（大号超粗 + 负字距），必须换掉——密度目标下这是浪费。

### 6.6 主题页 `/topics` 与 `/topics/:slug`

**现状**：按分组（`groups`）分区，每区标题 + `blurb` 一句说明，`TopicCard` 在手机上是一条行、桌面是 3-4 列卡片网格（`lg:grid-cols-3 xl:grid-cols-4`）。

**问题**
1. `TopicCard` 手机行 / 桌面卡是**两套完全不同的视觉**（`lg:card lg:flex-col` 切了 7 个 utility），用户从手机到桌面得到的是两个产品。
2. **卡片网格全是同尺寸 + 图标 + 标题 + 两行文字 + 一行时间** —— 这正是我自己知识库里的「相同卡片网格」反模式，密度还低（`p-5`、`gap-3`、xl 4 列）。
3. 主题页是本项目**唯一的结构化检索入口**，应该像 Kitco 的品种导航 / Trading Economics 的分类页，但现在是杂志目录的形态。
4. `BrandMark`（品牌头像，30px/22px）在贵金属语境下语义不明——「黄金」这个主题不该有一个品牌头像。

**改成什么样**
- **统一为紧凑行列表，取消卡片**（密度 4 → 7）：
  - 每行 44px 高（触摸目标）：`主题名`（14px，`--font-num` 用于拉丁部分 / 中文常规）· 一行定义（12px `--ink-4`，单行截断）· 关联条数（12px tabular 右对齐，56px）· 最近事件相对时间（12px 右对齐，96px）· 一条 48px sparkline 或涨跌幅方块
  - `divide-y divide-line-soft`，无卡片、无圆角、无阴影。桌面 `xl:grid-cols-2`（**两列，不是四列**——中文定义句在四列下每列不足 200px 会截断成没用的碎句）
- **分组头升级为筛选条**：现状 `groups` 的标题 + blurb 改成横排可点击 chip（`全部 / 贵金属 / 大宗 / 股债 / 宏观`），选中用 `--accent` 下边线。`blurb` 降为 chip 的 `title` 提示。
- **新增「品种索引」区块（置顶）**：本站最常查的是品种而不是主题，所以 `/topics` 顶部加一张**无框品种矩阵表**：`品种 | 类别 | 最新价 | 日涨跌 | 30日涨跌 | 近 30 天事件数`。13px tabular 右对齐。这是 Trading Economics「分类页即数据页」的思路。
- `BrandMark` 在 `topics.tsx` 中移除（该页无品牌语义），保留在真正需要标识信源的 `all.tsx` / `item.tsx`。

**为什么**：本页从「杂志目录」变「检索索引」。密度从 4 到 7（行高 44px vs 卡片 ~150px，密度约 3.4 倍）。取消卡片解决「同尺寸卡片网格」反模式。品种矩阵表让用户在第一次进入时就建立「这站有数据」的认知。

### 6.7 关于页 `/about` + 更新日志 `/changelog` + 反馈 `/feedback`

**现状**：`about.tsx` 13.6KB，`changelog.tsx` 9.4KB，`feedback.tsx` 14.5KB，`terms.tsx` / `privacy.tsx` 用 `.prose-compact`。

**问题**
1. **`about` 从 AI 站的「关于 AIHOT」继承而来**，大概率含 LLM / 模型 / 生成流程的叙述。改造后内容与新定位不符，需要重写而非改造。
2. `.prose-compact`（15px/1.85 + `h2` 上 1.4em 边框 + `td:first-child` 加粗）是很不错的政策页排版，**保留**。
3. `changelog` 有未读点（`nav.ts` 的 `changelog: true`）——对财经站，「更新日志」的信息价值低于「数据源与口径说明」。

**改成什么样**
- **关于页重写为三段结构**（不再有 Hero 大图 + 渐变标题）：
  1. **这是什么站**（4 行正文 + 一条 `AU9999 | XAU | AG9999 | SC | AU2604 | US10Y` 式的品种代码行，mono 12px，`--accent` 无，纯 `--ink-3`）
  2. **数据从哪来、怎么算的**（信源清单表格：来源 / 覆盖品种 / 更新频率 / 口径说明；这是金融站信任的真正来源，比「我们是一群热爱 AI 的人」重要一个量级）
  3. **已知局限**（直接列出：`T+0` 报价延迟、汇率换算时点、非投资建议声明）。**金融站主动声明局限比隐藏它更能建立信任**，这是 Bloomberg / FT 的标准做法
- **更新日志降级**，在侧栏「更多」组保留但**移到最末**；首页 nav 的未读点移给「数据源状态」入口（新增：显示上次成功抓取时间 + 各源健康度）。这是投资者真正关心的更新信息。
- `terms` / `privacy` 只改文案（加「不构成投资建议」条款），排版不动。
- `feedback` 表单：14.5KB 的表单页，改动点只有一处——反馈分类下拉里加「数据错误」并置顶（金融站最常见的反馈是数据错），以及错误提示位置贴近字段（现状待前端核验，若在顶部则必须移到字段下方）。

**为什么**：P0-3 禁止空洞文案。`about` 页是全站最容易出现 AI 味的位置（「我们热爱 AI 与开源」这类）。用「数据源 + 口径 + 已知局限」替代「我们的愿景」，既符合 P0-3，又符合金融产品的信任结构。

### 6.8 全局外壳（Sidebar / TabBar / 顶栏）—— 改动清单

**现状**：`nav.ts` 的 `SECTIONS` 分「内容」6 项（精选/动态/热点榜/日报/主题/收藏）+「更多」4 项；`TabBar` 手机 4 tab（精选/热点/日报/我的）；侧栏 236px。

**问题**
1. **缺一个「行情」顶级入口**。全部 10 个导航项里没有一个是「看行情」。这是 6.1 要加的行情带带来的结构问题——用户需要能把行情带固定住。
2. 手机 TabBar 4 项已满，加「行情」需要取舍。
3. 搜索在桌面被藏在 `hidden lg:block` 里。

**改成什么样**
- `SECTIONS` 改为三组，**顺序与优先级按投资视角重排**：
  ```
  行情  —— 行情带（/quote，桌面可固定）、品种（/instruments）
  内容  —— 今日（首页）、热点榜、日报、动态、主题
  更多  —— 收藏、数据源状态、Agent 接入、反馈、更新日志、关于
  ```
  语义上「行情」是入口，「内容」是阅读；把行情提到与内容同级，而不是塞进内容组里。
- 手机 TabBar 保持 **4 项**（≤5 且 ≤4 更优）：`今日 / 行情 / 热点 / 我的`。把「日报」从 tab 移到「我的」和侧栏（日报的使用频率是每日一次，不是每天几十次打开；热点榜才是持续盯的）。**这与终端的优先级一致：日报是结算物，热点是过程。**
- **搜索提到顶栏**（桌面右侧，图标 `Search` 16px + 占位文字「搜品种 / 事件 / 报告」），`/` 快捷键聚焦，`Esc` 清空。顶栏同时放一个 16px `Search` 的手机版。
- 收藏（`starred`）保留，但从「内容」移到「更多」——收藏是回顾行为，不是每日主路径。
- 保留 `bleed` / `screens.ts` / `view-transition`（含手机 push/back 方向感）/ `prefers-reduced-motion` 完整实现——**这四项是现状的强项，一律不动。**

## 八、数字与行情的视觉规范（本站特有 · Spec 条款）

### 8.1 数字排版规则

| 项 | 规则 | 理由 |
|---|---|---|
| **字体** | 一律 `--font-num`（Roboto）+ `font-variant-numeric: tabular-nums` + `font-feature-settings: "tnum" 1, "lnum" 1` | 比例数字会让 `1,075.00` 与 `1,000.00` 列宽不同，表格无法纵向对齐 |
| **对齐** | 表格/列表内的数字**一律右对齐**（`text-align: right`）。文本列左对齐。**数字列的列头也右对齐**；文本列的列头左对齐 | 右对齐让个位数对齐在小数点后，是扫读数字的唯一正确解。列头与数据同对齐，读者不必二次定位 |
| **正负号** | **强制显式**。正数带 `+`（`+1.24%` / `+4,175.30`），负数带 `-`（`-0.86%`），零值显示 `—`（em dash，不是 `0` 也不是 `0.00`） | 颜色不能是唯一编码（WCAG 1.4.1）。色弱用户靠符号；`—` 让「零」与「无数据」在视觉上区分开（无数据用 `--ink-4` 的 `—`，零值用 `--flat` 的 `—`） |
| **颜色** | 三级：`--up`（常规涨）/ `--up-strong`（≥20px 的大号数值、卡片头条数字）/ `--up-soft`（行底、标签底）；跌与平同理。**平盘一律 `--flat` 灰，绝不用红绿** | 第三级灰是必需的：中国市场有大量「平盘」状态（`0.00%`），染成红或绿都是错的 |
| **单位** | **进列名，不进单元格**（列头写「最新价（元/克）」而不是每格写「元/克」）。例外：单位与数值差一个数量级（如「持仓量 12.4 万手」）时，数值进单元格、单位进列头且只写一次（`持仓量（万手）`） | 单位重复在每行会形成竖向噪音带，是财经表格最大的可读性杀手 |
| **小数位** | 价格按品种固定（黄金 2、白银 3、铂金/钯金 2、铜/原油 2、股指 2、收益率 2）；**涨跌幅统一 2 位**；成交量 0 位（用「万/亿」缩写）；持仓量 0 位 | 固定小数位是小数点垂直对齐的前提。同一列里小数位不同 = 无法对齐 |
| **千分位** | `,` 半角逗号（`4,175.30`），非中文全角 | 国内财经惯例。`font-feature-settings` 不含 `pnum` 时用手写格式化函数 |
| **零与 O** | 价格与代码混排处用 `.mono` + `slashed-zero`（`XAU` 与 `1,0X0.00` 不会混淆） | 行情场景的 `0`/`O` 混淆是真实事故来源 |
| **字号下限** | 数据文字**不得低于 11px**；表头/元数据 11px + `tracking: 0.02em`；单元格 13px；大号数值 16-20px | 现状正文 12px 是下限，11px 只给表头与单位 |
| **字重** | 表头 510；单元格数字 400（大号数值 590）；**表格数字一律不用浅灰** | 浅灰数字在浅底上对比度不足且读不出来 |

### 8.2 涨跌色（浅色主题 · 最终值）

| Token | 值 | 对 `--bg #F7F8F9` 对比度 | 可用场景 |
|---|---|---|---|
| `--up` | `#C0362C` | **5.19:1** · 过 AA | 13px+ 文本、图标、sparkline 上涨线 |
| `--up-strong` | `#A32A20` | 7.0:1 · 过 AAA | ≥20px 大号数值 |
| `--up-soft` | `rgba(192,54,44,0.08)` | — | 行底、徽章底（**不可用于文字**） |
| `--down` | `#14804F` | **4.67:1** · 过 AA | 13px+ 文本、图标、sparkline 下跌线 |
| `--down-strong` | `#0F6840` | 7.4:1 · 过 AAA | ≥20px 大号数值 |
| `--down-soft` | `rgba(20,128,79,0.08)` | — | 行底、徽章底 |
| `--flat` | `#59656B` | 5.64:1 · 过 AA | 平盘 / 无变化 |
| `--warn` | `#8A5E12` | **5.35:1** · 过 AA | 12px 风险提示文本可用 |
| `--alert` | `#B3261E` | 6.2:1 · 过 AA · | 极端波动，**每屏 ≤1 处** |
| `--metal-gold` | `#B8860B` | 2.9:1 · 仅图形阈值的边缘 | **仅图形**（图表线 / 1px 规则线）。**禁止用作文字色** |

**三个关键取舍说明**：

1. **涨红为什么不是 `#E74C3C`**：`#E74C3C` 在白底上 3.8:1，13px 文字不合格，且它是「警报橙红」，与 `--warn` 的风险语义撞色。深砖红 `#C0362C` 是**财务报表红**（中国交易所公告与财经媒体的标准红），5.19:1 过 AA，密集排布时不刺眼。
2. **跌绿为什么不是 `#27AE60`**：`#27AE60` 在白底上 **2.4:1**，完全不合格，且读起来像「操作成功」的绿色。深翡翠 `#14804F` 4.67:1，且在中国语境里是「跌」的约定色，不与 `--ok` 混淆（`--ok #2f7d5c` 语义已收窄为「操作成功」）。
3. **警示为什么是深铜棕而不是亮黄**：`#EAB308` 在白底上 1.9:1，12px 完全不可用（这是最常见的错误——很多站直接用 Tailwind 的 `yellow-500` 做警告色）。`#8A5E12` 5.35:1，且铜棕呼应金属题材而不落入「珠宝电商」。

```css
  text-align: right;
  font-variant-numeric: tabular-nums;
  font-feature-settings: "tnum" 1, "lnum" 1;
}
/* 语义色：三级 */

/* 最后一行去线 */

```

**五条铁律**
1. **无竖线**。竖线在多列时会形成栅栏，把数字切碎。
2. **无斑马纹**。有彩色数字时斑马纹会产生摩尔纹/脏感。用 1px `--line-soft` 横线即可分节。
3. **表头粘性**。密度 7 的表必然超一屏，列头必须常驻（`sticky top: var(--bar-h)`，`--bg` 底避免透叠）。
4. **hover 只改背景色**，不改 border-color —— 改边框颜色会让相邻行出现 1px 位移抖动。
5. **水平滚动时表头与首列同时冻结**（`position: sticky; left: 0` 于首列，`--surface` 底）。

# 附录 A（2026-10-05 追加）· 快照数据的视觉方案 + V3 字体决策

> 本附录是追加，不改写上文任何结论。上文 §5.2/§6.1 的行情带设计在此被**细化并修正**（三处修正见 A.5）。
> 触发原因：Spec 已锁定「每日价格快照做」，且 architect 查清 V1 闭环。快照是**数据不是新闻**，需要独立表达。

## A.0 先纠正三处认知（读代码得出，与直觉相反）

我读了框架代码，**「`isolated` 只是不进列表」这个理解是低估了**。实际上 `isolated` 的隔离比预期强得多，这直接决定了三个问题的答案。

### 纠正 1：`isolated` 会让条目**连详情页都没有**

`packages/backend/src/publication/rules.ts:33-35`：

```ts
export function hasItemPage(p: { visibility: string; sourceMode: string }): boolean {
  return p.visibility !== "withdrawn" && p.sourceMode === "editorial";
}
```

`hasItemPage` 要求 `sourceMode === "editorial"`。**`isolated` 源的文章一律没有 `/items/:id` 页面**，`detail.ts:80` 直接返回 `not_found`。所以「快照的标题会不会被读者看到」这个问题在**详情页层面已经自动解决了**。

### 纠正 2：`isolated` 被强制 `visibility = "withdrawn"`

`packages/backend/src/publication/publish.ts:277`：

```ts
// Material from an isolated source reaches no public surface at all: not even a detail page.
const visibility = source.participation_mode === "isolated" ? "withdrawn" : (override?.visibility ?? "public");
```

而三个列表条件全部要求 `visibility = 'public'`：

| 出口 | 条件 | 位置 |
|---|---|---|
| 时间线（`/all`、首页） | `selectedCondition` → `p.visibility = 'public' AND p.selected AND p.visible_after <= now` | `scope.ts:27-29` |
| RSS | `seatedCondition` | `scope.ts:35-37`、`feeds.ts:155` |
| 公开 API v1 | `listedCondition` / `seatedCondition` | `scope.ts:17-19`、`v1.ts:62` |
| 热点榜信号 | `WHERE s.participation_mode <> 'isolated' AND coalesce(p.visibility,'public') <> 'withdrawn'` | `events/hot.ts:125` |

**结论：快照对全部公开出口零暴露，且是框架保证的，不依赖我们前端自觉。** 这比 team-lead 假设的「靠 `participation_mode` 挡住」更严密——是**双保险**（源级 `isolated` + 单条级 `withdrawn`）。

### 纠正 3：但有一个真实泄漏点，必须处理

`events/group.ts:298`：

```ts
if (opts.signalOnly || a.participation_mode !== "editorial") return groupSignal(a, source, observedAt);
```

**非 `editorial`（含 `isolated`）的条目会走 `groupSignal`**，而 `groupSignal` 在 embedding 召回命中时会 `recordSignal()`（`group.ts:122-133`），那条 SQL 会**改写 `stories.latest_at` 与 `first_report_at`**：

```sql
UPDATE stories SET latest_at = GREATEST(...), first_report_at = LEAST(...)
```

`latest_at` 决定事件在 `/story` 列表与 sitemap 里的排序。**后果**：每天一条的价格快照会给「黄金相关事件」持续续命，让一个三天前的旧事件在「最新事件」里长期置顶，而读者在事件页**看不到任何快照内容**（因为信号查询过滤了 `isolated`）。这是**读者可见的时间线污染，且没有任何提示**。

**这必须请 architect 处理**（不是设计能解决的）。三个方案，我推荐第2 个：
1. `groupSignal` 入口对 `isolated` 直接短路返回 `signal-unmatched`（最省，但改热榜计算路径）
2. **`recordSignal` 里对 `kind='signal'` 且源为 `isolated` 的行跳过 `UPDATE stories`**（精准，只影响这一个副作用）
3. 快照 `title`/正文里塞入不可召回的标记词（ hacky，不推荐）

**设计侧的兜底（无论架构怎么改都要做）**：事件页的「最新动态」时间必须**只读可见证据**的时间。若架构不改，则事件排序在快照上线后会出现「时间很新但内容很旧」的条目，**这在设计上是不可接受的**。

## A.1 三个问题的正式回答

### Q1：`/all` 要不要显示快照？——**不显示，且这不需要我们做任何事**

`selectedCondition` 要求 `visibility = 'public'`，而 `isolated` 强制 `withdrawn`。**框架已经保证了 `/all` 不会出现快照。** team-lead 的倾向正确，且是零成本。

**但要补一条设计约束**：`/all` 的「6 分类筛选 + 13 品种标签筛选」里，**不要出现「价格快照」这个分类或标签**。如果 taxonomy 里给它留了位置，筛选项会显示成一个永远为空的选项——这是空状态设计失误。SPEC 9.15 的 13 个品种是新闻品种标签，**快照不进这 13 个**（它不是新闻标签）。

### Q2：快照进不进事件归组？——**架构层已排除展示，但会污染时间戳（见 A.0 纠正 3）**

- **展示层：完全不会出现在事件页**。`currentSignals()`（`events/hot.ts:111-129`）有 `s.participation_mode <> 'isolated'` 硬过滤，`stories.ts:141` 的事件证据查询复用它。**这条确认成立。**
- **时间戳层：会污染**。见 A.0 纠正 3，需 architect 修。

**给architect 的正式请求**（请转达）：

```
请在 packages/backend/src/events/group.ts:122 recordSignal() 里，
对 kind='signal' 且 source.participation_mode='isolated' 的情况
跳过 UPDATE stories ... latest_at / first_report_at，
只 INSERT story_signals（或整条短路返回）。
理由：每日价格快照不应改写事件时间线排序。
最小改动，不触碰热度算法。
```

### Q3：快照的标题怎么写？——**面向机器，不面向读者**

因为纠正 1+2 已经确定标题**不会有任何读者看到**（无详情页、不进列表、不进 RSS/API），所以标题的读者是**运营和未来的自己**。

现在的 `黄金 XAU 快照 2026-10-05` 有两个问题：
1. 「快照」对运营无信息量——她关心的是**这条能不能用**
2. 缺价格，排查时得进数据库看

**建议改为**：

```
[XAU] 黄金 4,137.30 · 2026-10-05T13:24Z
```

- `[XAU]` 方括号前缀 → 在后台列表里一眼识别，且**排序时聚在一起**
- 品种中文名 → 运营可读
- **价格进标题** → 排查时不用进数据库；也让它在 `identity_key` 冲突时提供视觉区分
- ISO 时间戳带时区 → 与 `published_at` 一致，避免时区歧义

**关键约束（写给前端/脚本）**：标题里**绝不能放会变的值**。`title` 参与 `content_hash` → 变了就 `reviseMaterial()` → 整条管道重跑。价格**每天都在变**，所以：

> **价格不能进 `title`，只能进 `raw`（JSONB）。** `title` 只能是「静态描述 + 日期」。

修正后的建议格式：

```
[XAU] 黄金价格快照 · 2026-10-05
```

- 日期进标题是安全的（每天一个 identity_key，本来就是新文章）
- 价格、涨跌幅、时间戳全部进 `raw`： `{symbol, name, price, updatedAt, prevPrice, changePct, source: "gold-api"}`
- 这样 `title` 每天只变一次（日期），`content_hash` 每日一变→ 走新文章路径，**不触发重跑**

## A.2 涨跌幅基准：这是本附录最关键的设计决策

### 实测结论

我实测了 `api.gold-api.com/price/XAU`：

```json
{"currency":"USD","currencySymbol":"$","exchangeRate":1.0,"name":"Gold",
 "price":4137.299805,"symbol":"XAU","updatedAt":"2026-10-05T05:24:37Z",
 "updatedAtReadable":"a few seconds ago"}
```

**确认 team-lead 的判断：只有 `price` 与 `updatedAt`，无 `previousClose`、无 `changePct`、无 `open`/`high`/`low`。** 所以涨跌幅**必须自己算**。

### 三个选项的裁决

| 选项 | 裁决 | 理由 |
|---|---|---|
| ① 用 `articles` 表历史自算 | **采纳** | 零新增依赖、零新增信源、框架天然有历史（每日一条，identity_key 含日期） |
| ② 不显示涨跌幅只显示价格 | 拒绝 | **这是不可接受的**。涨跌幅是行情带的灵魂，砍掉它就退化成一个静态数字表，用户没有任何理由每天回访。首页沦为摆设 |
| ③ 换一个带涨跌幅的免费接口 | 拒绝（但保留为升级路径） | 引入新信源 = 新的失败模式、新的合规审查、新的 SPEC 变更。V1 不该为一个字段付这个成本。**但把这个接口记在 §10 的升级路径里** |

### 采纳方案 ① 的完整设计

**数据获取**（零新表，零新信源）：

```
articles 表 · identity_key LIKE 'url:https://snapshot.metalsmacro.local/{symbol}/%'
取该 symbol 最近 2 条（含今日），从 raw->>'price' 读出
```

**关键设计决策：涨跌幅的口径必须诚实标注。**

这是最容易出事的地方。我们算的是「今日快照价vs 昨日快照价」，**这不是金融意义上的日涨跌幅**（后者以昨收/结算价为基准）。如果标成「日涨幅」，懂行的读者会发现口径不对——**这比不显示更糟**。

**因此定名如下（不可改）**：

| 场景 | 标签 | 口径说明 |
|---|---|---|
| 基准是**昨天**的快照 | `较昨日` | 最常见情形，tooltip 写「对比 {日期} 13:24 快照价」 |
| 基准是**上一条**快照（跨过一天没跑） | `较上次` | **诚实优先于好看**。周末/节假日/脚本漏跑时用这个标签，不假装是「昨日」 |
| **无基准**（首次运行，或昨日脚本失败） | `—` + `--flat` 灰 | **绝不用 `0.00%` 或 `—0.0%` 冒充**。这是一条硬规则：无数据就是无数据 |

**「较上次」这个状态是常态而非异常**：脚本每天跑，节假日也会跑，所以大多数时候是「较昨日」；但只要有一天漏跑（网络失败、gold-api 挂了），第二天就自动变成「较上次」——**这个设计让系统在说谎时自动降级，而不是给出看似正常的错误数字**。这比任何错误提示都更可靠。

### 涨跌幅的三个边界情况（必须处理，否则会显示错误数字）

| 情况 | 判定| 显示 |
|---|---|---|
| 无前一条快照（首次运行） | `prevPrice == null` | `—`，`--flat` 灰，不显示箭头 |
| 今日 == 昨日（脚本重跑同一天） | `price == prevPrice` | `0.00%`，`--flat` 灰，**不显示箭头**（`±0.00%` 是噪音） |
| 昨日脚本失败 / 断档 > 3 天 | `gapDays > 3` | 仍显示涨跌幅，但标签用 `较上次` 且**加 `--warn` 的 `TriangleAlert` 14px 图标**，tooltip 写明真实基准日期 |

第三条最容易漏。**如果基准是 5 天前的，涨跌幅的数字会让人误以为是日涨跌** ——这在金融站是硬伤。加一个 14px 警示图标是最低成本的诚实表达。

### 小数位（按品种固定，这是对齐的前提）

| 品种 | 代码 | 小数位 | 单位 | 说明 |
|---|---|---|---|---|
| 黄金 | `XAU` | **2** | 美元/盎司 | |
| 白银 | `XAG` | **3** | 美元/盎司 | 银价本来就在 cents 以下，2 位会丢信息（实测约 4100美元时 2 位尚可，但 30 美元时必须 3 位） |
| 铜 | `HG` | **2** | 美元/磅 | **注意：铜是美元/磅不是美元/吨**，gold-api 返回 COMEX 铜，单位与金银不同，**必须在 tile 上标单位** |
| 铂金 | `XPT` | **2** | 美元/盎司 | |
| 钯金 | `XPD` | **2** | 美元/盎司 | |

**铜的单位差异是我实测gold-api 后最想强调的一条**：贵金属是美元/盎司（troy ounce），工业金属是美元/磅（lb）。**如果行情带不标单位，读者会把 4.1美元的铜和 4100 美元的金放在一起比较量级**，这是严重误导。

**因此 `QuoteTile` 底部必须有单位行**（A.3 给最终形态）。这是「单位进列名」原则在 tile 上的应用——tile 太窄放不下列名，所以单位作为 tile 的固定第三行。

## A.3 行情带最终形态

### 五个品种的展示顺序：**黄金 → 白银 → 铂金→ 钯金 → 铜**

**不按 API 返回顺序**（gold-api 按 URL 里传什么返回什么，没有内在顺序，且可能变化——**UI 顺序绝不能依赖外部 API 的返回顺序**）。

**不按纯流动性**（虽然流动性大致是金>银>铜>铂>钯）。

**最终顺序的理由（三条，按权重）**：

1. **黄金第一，无可争议**。它是站名主题，是全站唯一被反复提及的标的，用户进站第一眼要看的就是它。流动性也最高。
2. **贵金属聚在一起，铜单独垫底**。站的分类是「贵金属 + 大宗商品」，前4 格是贵金属（4 种），第 5 格是大宗商品（1 种）。**顺序本身就是分类信息** —— 这比在 tile 上加分类标签更省像素。
3. **铜垫底而非插在中间**。若按流动性排成「金银铜铂钯」，贵金属会被铜劈成两半，读者要重新扫一遍才知道哪些是贵金属。**分组连续 > 单项最优**。

（顺序：黄金 → 白银 → 铂金 → 钯金 → 铜。若未来增加「原油」「美债」等，走同样的逻辑追加到末尾并保持同类连续。）

### `QuoteTile` 最终参数

**与原稿的差异（修正）**：

| 项 | 原稿（§8.4 形态 A） | **修正后** | 为什么改 |
|---|---|---|---|
| 高度 | 4 行，约 108px | **4 行但含单位行，92px** | 单位行是新增的必需项（A.2 铜单位问题）。压缩字号腾出空间，不加总高 |
| 价格字号 | 13px（`--text-data`） | **17px** | 原稿把价格和涨跌幅设成同号，导致价格不突出。**价格是这条信息的主体**，应比涨跌幅大 4px。这是原稿的一个判断失误 |
| 品种码 | 未定 | **用交易码（`AU9999`/`XAG`/`HG`）而非品种名** | 交易码是读者实际下单/查行情用的标识符。中文名（黄金/白银）信息量低且占宽度。**但鼠标 hover / 手机长按显示中文名** |
| sparkline | 60px 宽 | **取消 sparkline** | 见下|

**为什么取消 sparkline**（这是我读完架构后改的主意）：

sparkline 需要历史价格序列。要拿到它得查 `articles` 表该symbol 的全部历史快照，**V1 每天只有1 条**，也就是说**上线第一天 sparkline 必然是空的，第二天才有 1 个点**。一个 60px 宽、只有 1-2 个点的折线不是信息，是**视觉噪音的替身**。

而且更根本的问题：**快照是每日一条的单点数据，sparkline 表达的是「趋势」，而每日单点没有趋势**。要表达趋势至少要 7-14 天的连续点位，那要等两周后才可能好看。

**决策：V1 行情带不放 sparkline。** 用节省下来的 32px 高度做两件更实在的事：把价格放大到 17px，以及加单位行。

**升级路径**（记在 §10）：当 `articles` 积累 ≥14 天历史后，**在事件详情页的 `QuotePanel` 里加7 日sparkline**（那里有单一品种的完整语境，比首页并排 5 个 tile 更适合放趋势图），**首页行情带保持无 sparkline**——5 个并排趋势线在116px 的格子里看不清，只会变成五条噪音线。

**行情带的容器形态**：

```css
/* 行情带：首页置顶，无框通栏 */
.quote-bar {
  display: flex;
  gap: 0;                          /* 用 1px 竖线分格，不留空隙 */
  overflow-x: auto;                /* 手机横向滚动 */
  background: var(--surface);
  border-block: 1px solid var(--line);   /* 上下 1px 线，无圆角无阴影 */
}
.quote-tile {
  flex: 0 0 auto;
  width: 116px;                    /* 手机 104px */
  padding: var(--space-3);         /* 12px 上下左右 */
  border-right: 1px solid var(--line-soft);
  position: relative;
}
.quote-tile:last-child { border-right: 0; }
```

**为什么上下 1px 线、格间1px 竖线、无圆角无阴影**：这是 DENSITY 7 的直接落地。行情带是**数据容器**不是**卡片容器**——`border-block` 把它和上下内容分隔开（替代卡片阴影的分组作用），格间竖线替代卡片间距（替代卡片边框的边界作用），`border-right` 在 1px 的 `--line-soft` 而不是 `--line`，保证视觉重量低于上下边线。**圆角会让相邻格出现圆角对不齐的破口，所以行情带一律 0 圆角。**

**「数据截至」提示**（必做，且位置固定）：

行情带**下沿**右侧，`11px --ink-4`：`数据截至 10-05 13:24`。若脚本失败或数据超 6 小时，改为 `--warn` 色 + 前面加 14px `TriangleAlert` 图标 + 文案改为 `行情数据可能已过期`。

**这个提示不能省**。金融站的行情数据一旦过期而不说，读者会拿旧价格做判断——这是**信任问题不是设计问题**。而且成本极低：一个 11px 的行。

###行情带的 5 态（继承 §7.4 并细化）

| 状态 | 行情带的显示 |
|---|---|
| **Loading** | 5 格骨架（复用 `.skeleton`），价格行灰块，**不显示 0.00** |
| **Empty** | 「行情数据尚未生成」+ 一行说明 + 不显示任何价格数字。**绝不用 `—` 填满 5 格当装饰** |
| **Error** | 整带替换为一条 1px `--warn` 提示条 + `行情源暂不可用` + 14px `TriangleAlert` + 下方事件流**照常显示**（数据层与内容层解耦） |
| **Populated** | 正常 5 格 |
| **Edge · 断档** | 基准 >3 天的那格：涨跌幅后加 14px `--warn` `TriangleAlert` + 标签用「较上次」（A.2） |

**单格失败不影响其他格**：某品种取不到时该格显示 `--ink-4` 的 `—`，**其余 4 格正常显示**。整带因1 格失败而不可用是最差实现。

## A.5 V3 字体决策：自托管，**不用 swap**

### 结论

**采纳自托管**（30-40KB 放`public/fonts/`），**`font-display` 用 `block` 而非 `swap`**，并做 3 项优化。

### 为什么不 CDN

本机开发、可能无外网。CDN 挂掉时`swap` 会让页面**先用系统字渲染、再切换成 Roboto** —— 在数字场景下这是**灾难**：价格会先按 Segoe UI 的比例数字排版（列宽不对），再跳成 Roboto 的等宽数字（列宽变了）。**行情表的列宽会闪一下然后重排**，这正是我们花大力气用 `tabular-nums` 要避免的事情。

### 关键决策：`font-display: block`（不是 swap）

这是个反直觉但正确的选择：

| 值 | 行为 | 本站是否可用 |
|---|---|---|
| `swap` | 字体没加载完就用fallback 渲染，**加载完再换** | **不可用**。会先渲染比例数字再跳成等宽数字，**表格列宽重排** |
| `fallback` | 100ms 极短阻塞，之后永久用 fallback | 次优。等太久 |
| `optional` | 100ms 内能加载就用，否则本次会话永久不用 | 次优。**若字体已在 HTTP 缓存里，体验好；首访会降级** |
| **`block`** | **最多阻塞 3s（可设），期间文字不可见（FOIT）** | **本方案采用** |

**`block` 为什么对**：本地 30-40KB 的 woff2 从 localhost 读取是**毫秒级**的。`block` 期间用户看到的是空白而非错位数字，3s 远不会触发。**「等一下」比「看到错的数字然后跳一下」好得多。**

**配套措施**：给 `block` 设一个短超时，避免极端情况下白屏 3s：

```css
@font-face {
  font-family: "Roboto";
  src: url("/fonts/Roboto-400.woff2") format("woff2");
  font-weight: 400;
  font-display: block;   /* 关键：不是 swap */
}
/* Roboto Condensed 仅用于标题，权重少，体积更小 */
@font-face {
  font-family: "Roboto Condensed";
  src: url("/fonts/RobotoCondensed-600.woff2") format("woff2");
  font-weight: 600;
  font-display: block;
}
/* Roboto Mono 仅用于代码与 .mono，Arabic/Persian 数字区不用 */
@font-face {
  font-family: "Roboto Mono";
  src: url("/fonts/RobotoMono-400.woff2") format("woff2");
  font-weight: 400;
  font-display: block;
}
```

**3 项优化（降低首屏成本）**：

1. **只自托管必需的 3 个文件**：`Roboto-400`（正文 + 数字，**最重要**）、`RobotoCondensed-600`（标题）、`RobotoMono-400`（代码）。**不托管 500/700**——正文只用 400（Windows 中文字体只有 400/700，见下），标题用 Condensed 600 区分层级。省下的体积直接减首屏。
2. **只 preload 一个**：`Roboto-400.woff2`（它服务正文和**所有数字**，是首屏最关键的一个）。Condensed 与 Mono 不 preload（标题在首屏下方，代码块在正文末尾）。
3. **中文字体不打包 webfont**：走系统栈 `PingFang SC`（macOS）→ `Microsoft YaHei`（Windows）→ `Noto Sans SC`（兜底）。这是既定决策，不变。

### Windows 上的实际观感（这是最该验证的一点）

用户的运行环境是 **Windows +系统雅黑**，这带来三个必须说清的事实：

**事实 1：雅黑没有 400/700 之外字重。** `font-weight: 510` / `590` 在雅黑上会被**合成**（伪粗）或**回退**到 400。合成的中文粗体在 Windows 上会**发虚、边缘毛糙**——这是设计上要避免的。

**因此 Windows 下的字重策略必须落地为**：
- **中文正文只用 400**（不加粗）
- **中文标题用 700**（雅黑原生粗体，不合成）
- **`510` / `590` 只对拉丁字母与数字生效**（Roboto 有完整的 100-900，数字用 590 是安全的）
- **禁止让中文走 510/590**

这需要在 CSS 上做**显式隔离**，不是靠运气：

```css
/* Windows 雅黑只有 400/700。中文禁止合成中间字重。
   做法：把中间字重限制在拉丁/数字容器上，中文单独降级。 */
.num, [class*="mono"], .prose code { font-weight: 590; }  /* 数字可放心用 590 */
:lang(zh) { font-weight: 400; }
h1, h2, h3, .prose strong { font-weight: 700; }             /* 中文标题用原生 700 */
```

**事实 2：雅黑的西文字形与 Roboto 混排会「基线不齐」。** 雅黑的拉丁部分字面偏小、行高偏大，和 Roboto 放一起会显得中文比数字「大一号」。**这是中英混排的固有问题，不是 bug**。缓解办法：给含数字的行**不要单独放大字号**（价格 17px 时，数字用 17px 而中文单位行保持 11px，靠位置区分大小而不是靠同字号内的字体差异）。

**事实 3：`.mono` 的 0.92em 缩放对 Roboto Mono 依然必要。** Roboto Mono 的字面偏大偏宽，14px 时比同尺寸 Roboto 视觉重量高。**0.92em 这个值在换字体后必须重新目测**，初值不变但要在 Windows 上验。

### 首屏影响结论

| 方案 | 首屏影响 |
|---|---|
| CDN + `swap` | **不可接受**：表格列宽会闪一下再重排（比例数字 → 等宽数字） |
| 自托管 + `swap` | 仍不可接受：本地也可能是首次未缓存，swap 的重排问题依然存在 |
| **自托管 + `block` + 只preload 400** | **本方案**：30-40KB 从 localhost 读取是毫秒级，阻塞期用户看到空白而非错位数字。**列宽不会重排** |

**一句话给前端**：`font-display: block` 是本项目的一个反直觉决定，理由是 `swap` 会让行情表列宽在首屏重排一次。**实现时不要"顺手改成 swap"。**

## A.6 一个必须记录的自查修正

我在 §8.2 写「`--metal-gold #B8860B` 2.9:1，仅图形」。**这个数字算错了**。实测：

| 底色 | 对比度 | 判定 |
|---|---|---|
| `#B8860B` on `#F7F8F9` | **3.06:1** | 过 WCAG 1.4.11 非文本 3:1 |
| `#B8860B` on `#FFFFFF` | 3.25:1 | 过 |

**修正**：`--metal-gold #B8860B` 实际 **3.06:1**，**满足** WCAG 1.4.11 对非文本对比（3:1）的要求，可以用于**图形**（黄金的 1px 规则线、图表曲线）。原文写的「2.9:1 / 仅图形阈值的边缘」是保守误判。

## C.3 architect 发现的并发锁陷阱：我的方案和它的方案都有这个bug

这是本轮最重要的产出，**且它推翻了我在 B.3 给architect 背书的那个方案。**

#### 那个锁是什么

`group.ts:122-127`：
```ts
const updated = await db`UPDATE stories SET ... WHERE id = ${storyId} AND merged_into IS NULL`;
if (!updated.count) throw new Error("Grouping target changed; retry against the current story");
```

**`AND merged_into IS NULL` + `if (!updated.count) throw` 不是为了刷新时间戳，而是一道并发合并保护**：story 若在这期间被合并进别的 story，UPDATE 影响 0 行 → 抛错 → 让调用方重试到合并后的 story。

#### 跳过整个 UPDATE 会静默破坏它

`story_signals` 的表定义（`0002_events_reports.sql:82-90`）：
```sql
story_id bigint NOT NULL REFERENCES stories (id) ON DELETE CASCADE,
...
PRIMARY KEY (story_id, article_id)
```

**只有 FK，没有「目标 story 未被合并」的约束。合并后的 story 行仍在，所以 INSERT 不会报错。**

后果链：
```
若为 isolated 跳过整个 UPDATE
→ 锁消失，story 合并期间不再抛错
→ story_signals 静默写到已合并的 story 上（不报错）
→ currentSignals() 会把它算进热度
→ 比原问题更隐蔽
```

**这意味着我背书的 `touchStory = true` 方案是错的**——它和我原方案的「改签名」一样，都在跳过整个 UPDATE。我在 B.3 说「你的方案冲突面最小、我采纳」时，没有意识到它引入了这个更隐蔽的 bug。**这是我的判断失误，我撤回那个背书。**

#### 唯一正确的写法：`CASE WHEN`，UPDATE 与抛错一行不动

```ts
const touch = source.participation_mode !== "isolated";
const updated = await db`UPDATE stories SET
    latest_at       = CASE WHEN ${touch} THEN GREATEST(coalesce(latest_at, ${observedAt}), ${observedAt}) ELSE latest_at END,
    first_report_at = CASE WHEN ${touch} THEN LEAST(coalesce(first_report_at, ${observedAt}), ${observedAt}) ELSE first_report_at END,
    updated_at      = CASE WHEN ${touch} THEN now() ELSE updated_at END
  WHERE id = ${storyId} AND merged_into IS NULL`;
if (!updated.count) throw new Error("Grouping target changed; retry against the current story");
await db`INSERT INTO story_signals (...) ON CONFLICT (story_id, article_id) DO NOTHING`;
```

- **并发锁完整保留**（UPDATE 仍执行，`updated.count` 仍可能为 0，仍抛错）
- 三个时间戳列在 `touch=false` 时**原值不动**
- `story_signals` 的 INSERT 一行不改
- 需要的只是 `source` 参数类型加 `participation_mode`，三个调用点里**只有 `group.ts:563` 需要区分**

**这就是 architect 在 SPEC §9.3 写的「绝对不能跳整个 UPDATE」。** 我已核实其正确性。

**成本从 0.2 人日回到 0.3 人日**（改签名 + 一处调用点传参 + 三列 CASE WHEN，比加一个可选参数略多）。我上轮报的 0.2 人日是基于错误方案的估算，作废。

# 附录 E（2026-10-05 追加）· 采纳读侧改法，并补一条更硬的回归证据

> 触发：architect 采纳我的「纯读侧改`sitemap.ts`」方案并给出 `LEFT JOIN LATERAL` 的回归风险。**他的风险判断成立，且我找到了比他给的更硬的证据。**

## E.1 architect 的「现成范式」论证比我原来的理由更硬

我原来提读侧改法的理由是「风险更小」。**这个理由偏弱——「更安全」是主观判断，评审时容易被质疑「那到底有多安全」。**

architect 找到了决定性理由：**`publication/hot.ts:36` 已经在做一模一样的事**：

```ts
JOIN LATERAL (
  SELECT max(coalesce(p.published_at, p.discovered_at)) AS at
  FROM facts f JOIN fact_articles fa ON fa.fact_id = f.id JOIN publications p ON p.article_id = fa.article_id
  WHERE f.story_id = st.id AND ${evidenceCondition()} AND ${listedCondition(now)}
) latest ON true
...
latestAt: report.latest_at.toISOString(),
```

**取可见证据的最大时间，而不是读 `stories.latest_at` 列。** 所以这个改法不是「新发明」，而是**把 `hot.ts` 已有的正确做法搬到 `sitemap.ts`**。我已核实该处代码确实存在（`hot.ts:30-45`），且 `publication/hot.ts:49` 的 `latestAt` 用的就是这个 LATERAL 的值。

**一致性本身就是最好的评审理由**——同一个概念（事件最后可见进展）在两处用同一种算法，不需要论证「哪个更对」。

---

## E.2 回归风险成立，且框架自己的注释就承认了这个场景

architect 提示 `LEFT JOIN LATERAL` 的风险：**若某story 有 editorial 事实但因 `releasedCondition(now)` 时间窗未命中，LATERAL 返回 NULL，裸写会让原本可见的 story 从 sitemap 消失。**

**这个判断正确，而且不需要推断——框架自己在 `stories.ts:157` 写了注释：**

```ts
// Historical stories without listed evidence retain their latest readable report.
const latest = text.latest ?? latestReport;
```

**框架明确承认「存在没有 listed evidence 的历史 story」**，并用 `?? latestReport` 兜底。所以：

| 写法 | 后果 |
|---|---|
| 裸写 `vis.latest_at AS latest_at` | **回归**：无 listed evidence 的历史 story 从 sitemap 消失。**这比 `lastmod` 失真严重得多**——失真只是数据不准，消失是页面进不了搜索引擎 |
| `coalesce(vis.latest_at, st.latest_at)` | 安全：LATERAL 为 NULL 时回退列值，最坏情况退回到当前行为（即失真），不会更差 |

**所以 `coalesce` 兜底是必须的，且它的失败模式是「退回现状」而不是「引入新问题」。** 这正是让一个修复可以安全上线的关键性质。

我另外核实了一处architect 提到的细节：**`ORDER BY` 确实要跟着改**（select 列表位置变了），architect 给的 `ORDER BY 4 DESC NULLS LAST, st.id DESC` 是对的。但我建议**用列别名而不是位置**（`ORDER BY coalesce(vis.latest_at, st.latest_at) DESC`）——位置序号在 select 列表变更时会静默错位，而别名不会。**代价是重复一次表达式，收益是不会因为将来有人在前面加一列而静默出错。**

---

## E.3 框架内已有两处 LATERAL 范式，join 类型不同且各有理由

我核对了全部 6 处 LATERAL 用法，**发现一个对本次改动有参考价值的事实**：

| 位置 | join 类型 | 场景 |
|---|---|---|
| `publication/hot.ts:36` | **`JOIN LATERAL`**（INNER） | 外层已有 `evidenceCondition`+`listedCondition` 硬过滤，LATERAL 必然有行 |
| `publication/story-text.ts:33` | **`LEFT JOIN LATERAL`** | 历史 story 可能无 listed evidence，**必须 LEFT** |

**所以 architect 说「`LEFT JOIN LATERAL` + `coalesce` 兜底」是符合框架既有范式的**——`story-text.ts` 就是这个组合（LEFT + 后续 `?? latestReport` 兜底）。**这不是新模式，是把story-text.ts 的模式搬到 sitemap。** 连兜底策略都一致（一个用 SQL `coalesce`，一个用 TS `??`，等价）。

这条让整个改动的说服力闭环了：**范式现成 + join 类型有先例 + 兜底策略有先例。**

## F.4 涨跌幅渲染规则（最容易做错的地方）

```
基准是昨天快照      → +1.24%     --up，无图标
基准是上一条快照    → +1.24%     --up，前置 14px TriangleAlert（--warn），title 写真实基准日期
基准断了 >3 天     → 同上（--warn 图标必须出现）
无基准（首次运行）  → —          --flat，无箭头
涨跌为 0│ 0.00%     --flat，**无箭头**
```

**三条硬约束**：
1. **绝不用 `0.00%` 冒充「无数据」**——无数据显示 `—` + `--flat`
2. **颜色 + 显式符号 + 方向箭头是三重编码**，不能只靠颜色（WCAG 1.4.1）
3. 断档 >3 天**必须**出现 `--warn` 图标，否则 5 天前的基准会被误读成日涨跌

行情带**下沿右侧**，`11px --ink-4`，文案 `数据截至 10-05 13:24`。

- 正常 → `--ink-4`

**不能省。** 行情数据过期而不说，读者会拿旧价格做判断——这是信任问题不是设计问题。成本是一个 11px 的行。

## G.1 `ReferenceTable` 降级态最终规格

**背景**：Spec §9.6锁了骨架（无边框 `divide-y`、行是品种码/中文名/N 条相关事件、底部诚实说明），但形态细节未定。frontend 已建 `features/quotes/ReferenceTable.tsx`（39 行），我核对其实现与本规格一致，以下是补齐的判定规则与它尚未处理的一处。

### 何时出现（三个条件同时满足）

| 条件 | 判据|
|---|---|
| 位置 | **仅**事件页/ 条目页左栏。**首页行情带永不降级成它** |
| 触发 | 该事件关联的品种**有快照但取不到价**（`price === null`），或快照链路整体失败 |
| 数量 | 关联品种为 0 时**整块不渲染**（`return null`），**不显示空壳** |

**为什么首页不能降级成它**：行情带是**固定的 5 个品种**（数据源驱动），`ReferenceTable` 是**从单个事件推导出的品种集**（内容驱动）。两者语义不同源。首页把行情带换成它，等于让这个模块**承诺了一件它不再是的东西**——读者昨天看到 5 个品种的价格，今天看到 3 个事件关联品种，会以为品种变了。**宁可整带显示 Error 状态并隐藏。**

### 行结构（每行 44px，触摸目标达标）

```
┌──────────────────────────────────────────────┐
│ AU9999    黄金                    3 条相关事件 │  ← 44px，divide-y
│ XAG       白银                    1 条相关事件 │
└──────────────────────────────────────────────┘
近 24 小时无该品种的价格快照。                  ← 12px --ink-4
```

| 元素 | 规格 |
|---|---|
| 容器 | **无边框、无圆角、无阴影**，仅 `divide-y divide-line-soft` |
| 行高 | **44px**（移动端触摸目标下限，`--row-h-list`） |
| 品种码 | `mono` 13px `tabular-nums` `tracking .08em`，`--ink-3`，**固定宽 52px**（保证多行时码列对齐） |
| 中文名 | 13.5px `--ink-2`，`truncate` |
| 事件数 | `tabular-nums` 12px `--ink-4`，`shrink-0`，格式 `{n} 条相关事件` |
| 底部说明 | 12px `--ink-4`，**必需，不可省** |

**三处容易做错的**：

1. **底部说明不能省。** 一张缺了价格列的品种表**看起来像 bug**，而且读者在别处被告知过「黄金 4100」时会以为数字马上出来。**这句话把「没有价格」从故障变成事实。**
2. **品种码列必须定宽。** 若不定宽，中文名长度不同会导致码列参差，**破坏 tabular-nums 的纵向对齐**——而这是全站数字纪律的基础。
3. **数量为 0 时整块不渲染。** 空壳比没有更糟：读者会以为「这个事件不涉及任何品种」是数据问题。

### 与有价态的切换

有价时事件页显示 `QuotePanel`（1px 边框 + 12px 圆角，每屏 ≤1）；无价时显示 `ReferenceTable`（无框）。**两者互斥，不同时出现。** 切换不应有动画——数据状态变化不是用户操作，不需要过渡。

### `eventCount` 的诚实性

`{n} 条相关事件`里的 `n` 必须是**该品种在站内的真实关联事件数**，不是「本文提到几次」。如果后端只能给出后者，**宁可不显示这一列**——显示一个含义错误的数字比留空更糟。这与 `unit` 必须进 `raw` 是同一条原则：**宁可缺字段，不可错字段。**
