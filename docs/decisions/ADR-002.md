# ADR-002: 锁定 Node 25.8.0 为最低可用运行时，PATH 优先级高于 workbuddy 内置的 22.22.2

## Status: Accepted (2026-10-05)

## Background

`package.json:13` 声明 `"engines": { "node": ">=24.11" }`。本机存在**两套 Node.js**：

| 路径 | 版本 | 来源 | 满足 engines？ |
|---|---|---|---|
| `C:\Users\23165\.workbuddy\binaries\node\versions\22.22.2-3\node.exe` | v22.22.2 | WorkBuddy 内置（`where node` 的**首位**） | [NG] |
| `D:\nodejs\node.exe` | **v25.8.0** | 用户手动安装 | [OK] |

`where node` 的输出顺序决定实际生效的版本，当前是 22.22.2。

这不是「低版本也能跑」的软性问题。`package.json:24` 的测试脚本：

```
"test": "node --test-global-setup=tests/databases.ts --import ./tests/databases.ts --test --test-concurrency=6 --test-timeout=120000 \"tests/*.test.ts\" \"modules/*/tests/*.test.ts\""
```

**实测验证（决定性证据）**：

```bash
# Node 22.22.2 —— 失败
$ node --test-global-setup=tests/databases.ts --test --test-name-pattern="__none__" "tests/databases.ts"
node.exe: bad option: --test-global-setup=tests/databases.ts

# Node 25.8.0 —— 通过（后续报错只是我故意给了不存在的测试文件）
$ /d/nodejs/node.exe --test-global-setup=tests/databases.ts --test --test-name-pattern="__no_match__" "tests/does-not-exist.test.ts"
Could not find 'tests/does-not-exist.test.ts'
```

即：**在Node 22.22.2 上 `npm test` 100% 失败**，且失败信息（`bad option`）与真实原因（Node 版本）毫无关联，排查成本高。

顺带验证的其他 flag：

| flag | 最低 Node 版本 | Node 22.22.2 | Node 25.8.0 |
|---|---|---|---|
| `--env-file-if-exists` | 22.9 | [OK] `env-file-if-exists OK` | [OK] `ok25 v25.8.0` |
| `--test-global-setup` | 23/ 24 | [NG] `bad option` | [OK] |
| 原生 TS 剥离 | 22.6（`--experimental-strip-types`） | [OK] `process.features.typescript === "strip"` | [OK] `strip` |

注意 `dev:api` / `dev:worker` 用的正是 `--env-file-if-exists`（`apps/api/package.json` 的 `dev` 脚本），Node 22.22 **能**跑开发模式。**所以本ADR 的影响面是测试与验收，不是日常开发。**

## Decision

**把 `D:\nodejs`（Node v25.8.0/ npm 11.11.0）作为项目唯一运行时，并确保它在 PATH 中优先于 WorkBuddy 内置的 v22.22.2。**

落地方式（三选一，按侵入性从低到高）：

1. **会话级（推荐，零配置）**：Git Bash 里 `export PATH="/d/nodejs:$PATH"`
2. **项目级**：在 `package.json` 里加 `preinstall` 检查，版本不满足就报错退出（需新增一个脚本文件）
3. **系统级**：Windows「环境变量」里把 `D:\nodejs` 上移到用户 `PATH` 之前

**不改 `package.json` 的 `engines` 字段**（`>=24.11` 是准确的），**不加 `engine-strict`**（仓库当前无 `.npmrc`，`npm ci` 在低版本上只警告不阻断——保持这个宽松行为，避免给团队其他成员添麻烦）。

## Consequences

### 正面

- `npm test` 可用，验收闭环
- `--env-file-if-exists` 也有富余余量（22.9 即可，25.8 远超）
- Node 25.8 是当前 LTS 线，活跃维护

### 负面

- **PATH 顺序是个隐式约定**。新开终端、换shell 环境、CI 环境都可能退回 22.22.2 → 再次遇到那条误导性的 `bad option` 报错
- Node 25 相比 24 在个别 flag 上有行为变化（如 V8 13.x 的默认参数），框架未在 Node 25 上做过完整回归
- 用户机器上两套 Node 共存，未来可能装第三套

### 内嵌坑（必须写进 Spec）

**内嵌坑 1**：`node_modules/` 是在哪个 Node 版本下装的会影响原生模块（`sharp`）的 ABI。**切换 Node 版本后必须重跑 `npm ci`**，否则 `sharp` 可能报 `invalid ELF` / 找不到模块。

**内嵌坑 2**：Node 22.22 上 `npm ci` 只警告不阻断（无 `engine-strict`），所以「装依赖成功」**不代表**「能跑测试」。依赖安装与测试运行要用同一个 Node。

## Alternatives Considered

| 方案 | 为什么拒绝 |
|---|---|
| 装 Node 24 LTS 并卸载/隐藏 v22.22.2 | 干净，但要动用户系统环境，且 WorkBuddy 自身依赖 v22 路径，改PATH 可能影响 WorkBuddy 运行 |
| 用 `nvm-windows` 管多版本 | 引入新的工具依赖，且 `nvm-windows` 在 Git Bash 下的行为需要额外配置；收益（版本切换便利）不足以抵消复杂度 |
| 改 `npm test` 脚本绕开 `--test-global-setup` | [NG] 该 flag 是 `tests/databases.ts` 的核心机制（第 43-49 行的 `globalSetup` 建库 + 迁移、第 62-71 行每文件建副本）。绕开它等于放弃「每个测试文件独立数据库副本」的隔离，测试会互相污染 |
| 装 Node 24.11 精确版本 | 25.8 已验证可用且是当前 LTS 追新版本，无需为「刚好够engines」而降级到旧版本 |
