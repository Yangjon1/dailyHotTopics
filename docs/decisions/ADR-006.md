# ADR-006: 行情播报在预筛层丢弃并打 standalone 标记，不改热度算法

## Status: Accepted (2026-10-05)

## Background

财经媒体一天会发几十条行情快讯：「纽约金价突破 2500 美元涨 2%」「COMEX 黄金涨 1.8%」「美债收益率上行 5 个基点」。这类内容有两个特征：

1. **不是事件**，是连续状态的一次读数
2. **同一状态会被反复播报**，一天可能十几次

框架的事件层有两个机制可能被它冲击：

**归组**（`industry/prompts/group-*.md`）：`group-definitions.md` 定义了四类关系`SAME_OCCURRENCE` / `SAME_STORY` / `UNRELATED` / `ROUNDUP`，**全部是「发生」的分类学**。价格突破会被判成`SAME_OCCURRENCE`（「多��媒体都在报同一件事：价格突破」），于是一个伪事件被建立。

**热度**（`packages/backend/src/events/hot.ts`）：

```ts
const WINDOW_HOURS = 48;      // 第 58 行
const HALF_LIFE_HOURS = 24;   // 第 59 行
const MIN_PARTICIPANTS = 2;   // 第 60 行
```

热度 = 48 小时窗口内、按 24 小时半衰期衰减的**参与来源数**加权。`currentSignals()`（第 113-129 行）的证据来自 `story_signals`，**每次采到该事件的报道就贡献一份证据**。

组合后果：**「金价2500 关口」这个伪事件会在 48 小时内持续霸占热点榜前列**（每条行情播报都加热它，半衰期 24h 意味着热度衰减很慢），而真正的「央行意外加息 50bp」只有 3 家媒体报道（`MIN_PARTICIPANTS=2` 刚过），热度反而更低。

**热度是错的吗？** 不是。热度算法准确反映了「多少独立来源在说这件事」——问题在于**输入层把行情读数当成了事件**。修输入比修算法更对。

## Decision

**三层处置，优先在输入层解决。改 `industry/prompts/` 与预筛结果落库处，不改 `packages/backend/src/events/hot.ts` 的热度公式。**

### 改法 A（必做，零模型增量成本）— 预筛层机械识别行情播报

改 `industry/prompts/prefilter.md`，加入**可机械判定**的行情播报识别规则（判据：有离散发生 → 保留；只有连续读数 → 丢）。详见 `02-architect.md` §4.3。

**为什么放预筛层**：预筛是每条资料必经的廉价步骤，在此处丢弃**不产生后续任何模型调用**（省 `score`/`structure`/`summarize`/`group` 共5-6 次调用）。这同时是成本优化。

### 改法 B（强烈建议）— 打 `standalone` 标记，让它不参与归组也不进热度

框架**已有**这个机制。`hot.ts:126` 显式排除：

```sql
AND NOT EXISTS (SELECT 1 FROM grouping_overrides go
                WHERE go.article_id = ss.article_id AND go.mode = 'standalone')
```

所以：预筛判定为行情播报的条目，在入库时写一条 `grouping_overrides(article_id, mode='standalone')` → **不参与归组、不进热度、不进热点榜**。

**改动点**：`packages/backend/src/content/materials.ts`（或 `ingest`）读预筛结果落库处，接上这个标记。**这利用了框架既有能力，不需要新表、不需要改算法。**

### 改法 C（可选，双保险）— 归组提示词加总则

在 `group-definitions.md` 顶部加一句总则：先问「有没有离散发生」。没有离散发生、只有连续读数的报道不是事件，`decisions` 全给 `UNRELATED`。这层是给改法 A/B 的漏网之鱼兜底。

## Consequences

### 正面

- 热点榜回归「事件」语义，**真事件获得应有的关注度**
- **成本下降**：行情播报在预筛被丢弃后，省掉后续 5-6 次模型调用。财经信源里行情快讯占比很高（估计 40-60%），这是**最大的单项成本优化**
- 不动框架核心代码 → 将来合并上游更新无冲突
- 复用 `grouping_overrides`既有机制，**不需要迁移**

### 负面

- **规则的准确性依赖提示词**。行情播报的形态千变万化（「Comex 黄金」这种无数字的标题也是行情播报），提示词可能漏判 → 改法 C 兜底，但仍可能漏
- 边界情况需要人工裁决：「CFTC 持仓报告显示基金净多头增加 5.2 万手」是数据发布（**保留**），而「黄金 ETF 持仓增加」（无具体主体和数据）可能是行情播报（**丢弃**）。这类边界要写进提示词的示例里
- 丢弃意味着**不可逆**：如果某条行情播报其实有决策价值（比如首次突破关键整数关口的分析），被丢了就是丢了。**缓解**：`docs/deploy.md`提到后台「内容诊断」可对单篇做处理，但丢弃的条目不在库里。→ **缓解措施**：改法 A 的判据写「宁严勿宽」——不确定是事件时**保留**（宁可多留一条，不要误丢真事件）

### 内嵌坑（必须写进 Spec）

**内嵌坑 1（`MIN_PARTICIPANTS=2` 与金融场景的关系）**：`hot.ts:185` 要求 `participants >= 2 && editorial_participants >= 1`。财经热点**确实**会有 2+ 家报道（路透+彭博+金十），所以这条**可以沿用，不需改算法**。但如果 PM 决定只接2 家媒体，热点榜会几乎全空。→ **信源数量与热点榜的可用性是耦合的**，PM 调研信源时需知悉。

**内嵌坑 2（`T1_5` 已在 3.x废弃）**：`docs/deploy.md:166` 记录「`T1` 就是一手，`first_party` 不再单独设置；以前单独标成一手的 `T1_5`、`T2` 信源不再算一手，要算就改成 `T1`」。但 `industry/selection.ts:17` 和 `hot.ts:35` 里 `T1_5` **仍在使用**。改造时若调整分级体系，需同步这两处（见 `02-architect.md` §4.6 的 `TIER_ORDER` 改动）。

**内嵌坑 3（热度榜只有 10 个席位）**：`hot.ts:190` 的 `if (entries.length >= 10) break`。三个板块（贵金属/大宗/股债）分10 个席位不够分。→ **列为待验证项 V2**，需 PM 明确热点榜的板块呈现需求后再定是否改成分类配额。

**内嵌坑 4（`ROUNDUP` 是行情播报的一部分归宿）**：`group-definitions.md` 已定义 `ROUNDUP`（综合稿与单事件报道不能合并）。财经媒体的「今日金价盘点」正是ROUNDUP。所以**多事件综合稿在金融场景大量存在且框架已支持**——问题只在「单一行情读数」上。

## Alternatives Considered

| 方案 | 为什么拒绝 |
|---|---|
| 改 `hot.ts` 的热度公式（给金融事件单独一套衰减/权重） | [NG] 改框架核心代码，将来合并上游冲突。且**问题根源在输入层**——把行情读数从事件流里去掉，比给它一套不同的热度算法更干净 |
| 只靠提示词（只做改法 A + C，不做改法 B） | [!]️ 有漏判可能，且漏判的条目会**完整走完 5-6 次模型调用**（浪费钱）后留在热点榜上。改法 B 是「判定即隔离」，成本更低 |
| 在 `hot.ts` 的 SQL 里加 `category NOT IN ('行情播报')` 过滤 | [NG] 同样要改核心 SQL，且这是把分类硬编码进引擎。`grouping_overrides` 是框架为「这类内容不参与事件计算」提供的正规机制，应该用它|
| 在 `prefilter.md` 里把行情播报判为低分（而不是丢弃） | [NG] **治标不治本**。低分条目仍会进 `structure`/`summarize`（要花钱），且如果分数仍在 `understandFloor: 50` 以上（`selection.ts:18`），还会被用「内容理解」的写法写一遍——更贵。**要在预筛阶段就丢掉** |
