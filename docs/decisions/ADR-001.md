# ADR-001: 采用 Windows 本机三进程 + Docker Desktop 仅承载 PostgreSQL

## Status: Accepted (2026-10-05)

## Background

本项目要把 AIHOT 开源框架改造成贵金属/大宗商品/股债行业热点站。团队约定开发环境为 **Windows 本机**：Node.js 直接跑三个进程（api / worker / web），Docker Desktop **只用来跑 PostgreSQL**。

框架官方文档 `docs/deploy.md:216` 明确写：「不用 Docker 需要 Node.js 24.11 以上和 PostgreSQL 16 或 17，**系统用 Linux 或 macOS；Windows 上请在 WSL2 里运行**」。这构成了一个需要澄清的官方支持矩阵问题。

关键问题是：**这条限制是代码层面的真实约束，还是仅仅是官方测试矩阵的边界？** 如果是前者，本机开发方案不可行；如果是后者，可以按用户约定的方式跑。

## Decision

**采用 Windows 本机三进程 + Docker Desktop 仅承载 PostgreSQL 的方案，不使用 WSL2。不修改框架核心代码。**

具体形态：
- `npm run dev:api` / `dev:worker` / `dev:web` 直接在 Windows 11 本机跑
- PostgreSQL 17 以单容器方式运行，端口绑`127.0.0.1:5432`
- 保留 `docs/deploy.md:216` 的官方支持矩阵表述不变，**追加**一节「Windows 本机开发（实验性）」记录实测配置

## Consequences

### 正面

- **无 WSL2 的性能与文件系统开销**（WSL2 的 `/mnt/d` 跨文件系统 IO 是Node 应用的已知性能陷阱，`node --watch` 尤其明显）
- 开发链路更短：改代码 → 热更新，不需要跨系统边界
- Docker 只承担单一职责（数据库），容器数量从 5 个降到 1 个，构建镜像的时间成本归零
- 保留生产可选性：将来要上服务器时，`docker compose up -d --build` 仍然可用（`docker-compose.yml` 未被破坏）

### 负面

- **偏离官方支持矩阵**，遇到框架 bug 时无法直接向官方求助，需自己定位
- Windows 上的 `sharp` 原生模块、`node --watch` 行为与 Linux 有细微差异，属「未官方验证」区域
- 备份策略需要另设（官方靠 `DB_BACKUP_STORE_*` + 容器卷；本机只有 Docker 卷，需手工导出）
- 团队其他成员若用macOS/Linux，需自行验证（本文档的验证步骤可复用）

### 已验证的证据

grep 全量验证，代码中**零POSIX 硬编码**：

```bash
grep -rn "process\.platform" --include=*.ts --include=*.tsx apps packages industry site scripts tests   # → 无输出
grep -rn "'/var/run|\"/var/run" --include=*.ts --include=*.tsx apps packages industry site scripts        # → 无输出
grep -rn "sh -c|execSync|/bin/sh" --include=*.ts --include=*.tsx apps packages industry site scripts     # → 仅代码高亮标签
grep -rn "path\.join('/'|path\.resolve('/'" apps packages industry site scripts tests                   # → 无输出
grep -rn "^\s*enum |namespace |import x = require" --include=*.ts apps packages industry site scripts      # → 仅SQL 关键字
```

- `tests/architecture.test.ts:26` 已做 `path.sep → "/"` 归一（`deploy.md:133` 记录了这次修复）
- 所有子进程调用用 `execFileSync(process.execPath, [...])`（数组传参），无 `sh -c` 字符串拼接
- 零非 erasable TS 语法（`enum`/`namespace`/参数属性）→ 可用 Node 原生类型剥离
- `pg-boss`（`packages/backend/src/jobs/queue.ts:64`）是纯 Postgres 队列，不触碰文件系统，无 Windows 行为差异

## Alternatives Considered

|方案 | 为什么拒绝 |
|---|---|
| WSL2 + 原生 PostgreSQL | 官方推荐，但 `/mnt/d` 跨文件系统 IO 显著拖慢 `node --watch` 与 57 个迁移的执行；且要求用户额外配置 WSL2 发行版与 systemd |
| 全Docker（`docker compose up -d --build`） | 每次改提示词/分类都要重建镜像（Dockerfile 第 22 行跑 `npm run build -w @aihot/web`），迭代循环以分钟计，不适合「边改边调门槛」的阶段 |
| Docker Desktop 跑 api/worker + 本机跑 web | 混合模式让 `AIHOT_DATA_DIR` 的路径语义在容器与宿主间不一致（`/data` vs 本地路径），调试时文件找不到，属最坏的混合 |
| Windows 原生装 PostgreSQL（不用 Docker） | 实测本机 `C:\Program Files\PostgreSQL` → `NOT_INSTALLED`，且原生安装的 `scram-sha-256` 认证会让 `deploy.md:227` 那种省略密码的 `DATABASE_URL` 写法失败。**保留为 Docker 不可用时的备选**（见 §1.3 方案 ②） |
